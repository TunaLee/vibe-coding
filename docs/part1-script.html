1-1 바이브코딩이란덱에서 보기

1바이브코딩 입문

반갑습니다. 시작하기 전에 고백 하나 하겠습니다. 저는 개발자입니다. 코드를 직접 한 줄 한 줄 쓰는 게 직업이었던 사람이에요. 그런 제가 현재는 코드를 거의 직접 안 씁니다. 바이브코딩으로 넘어왔거든요. 처음엔 저도 반신반의했습니다. 「말로 시켜서 만든 코드가 제대로 돌아가겠어?」 싶었죠. 그런데 써 보니 생각이 바뀌었습니다. 예전엔 며칠 걸리던 작은 도구를 한나절 만에 만들고, 남는 시간엔 「이걸 왜 만드는지」, 「제대로 만들어졌는지」를 고민하게 됐어요. 코드를 쓰는 손보다, 뭘 만들지 정하고 결과를 확인하는 눈이 더 중요해진 겁니다.

그리고 이게 여러분 이야기이기도 합니다. 이 눈은 개발자만 가진 게 아니에요. 오히려 매일 업무를 하면서 「이런 거 있으면 좋겠다」를 제일 많이 느끼는 분들, 바로 여러분이 더 잘 갖고 있습니다. 예전에는 그 아이디어를 개발팀에 요청하고 순서를 기다려야 했죠. 이제는 직접 만들어 볼 수 있습니다. 그래서 이 과정은 「코딩을 배우는 시간」이 아니라, AI한테 일을 잘 맡기고 결과를 제대로 검사하는 법을 같이 익히는 시간입니다. 개발자인 제가 바이브코딩으로 넘어오면서 부딪힌 것들, 시행착오까지 다 풀어 드릴게요.

한마디로 하면, 코딩은 더 이상 개발자만의 일이 아닙니다. 코드를 짜는 기술은 이제 AI가 누구에게나 똑같이 빌려줍니다. 개발자든 기획자든 사무직이든, 출발선이 같아진 거예요. 그럼 차이는 어디서 날까요? 누가 AI를 더 잘 쓰느냐입니다. 같은 AI를 써도 어떤 분은 원하는 걸 정확히 받아 내고, 어떤 분은 엉뚱한 결과만 받습니다. 그 차이는 타자 속도도, 전공도 아니에요. 무엇을 어떻게 맡기고, 돌아온 결과를 어떻게 확인하느냐의 차이입니다. 오늘부터 여러분과 함께 그 방법, 어떻게 하면 AI를 잘 쓸 수 있는지를 하나씩 배워 보겠습니다.

혹시 이 중에 코드 한 줄이라도 써 보신 분 계세요? 안 계셔도 괜찮습니다. 이 과정은 딱 그런 분들 기준으로 만들었거든요. 1부가 끝날 때쯤이면 여러분이 직접 기획한 작은 웹 앱을, 인터넷 주소 하나로 옆자리 동료한테 「이거 내가 만든 거야」 하고 보여 줄 수 있게 됩니다. 코드는 AI가 씁니다. 여러분은 사장님 역할이에요. 뭘 만들지 정하고, 다 만든 걸 검사하는 쪽입니다.

곁들일 이야기회의 메모는 메일에, 체크리스트는 엑셀에, 자주 쓰는 안내문은 카톡 나와의 채팅에… 이렇게 흩어 두고 쓰는 분 많으시죠. 그걸 한곳에 모으는 개인 메모장 정도가 1부에서 만들어 보기 딱 좋은 크기입니다. 오늘 하루 「나는 뭘 만들어 볼까」를 머릿속 한쪽에 켜 두세요.

2바이브코딩이란

첫 단원은 손은 쉬고 머리만 씁니다. 실습은 없어요. 바이브코딩이 대체 뭔지, AI는 어떻게 코드를 만드는지, 그럼 사람은 뭘 해야 하는지까지만 가볍게 짚고 넘어가겠습니다.

31부 커리큘럼

1부는 여덟 단원입니다. 1-1에서 감을 잡고, 1-2에서 계정과 도구를 챙기고, 1-3 기획서와 1-4 개발 계획으로 「뭘 만들지」를 글로 정리합니다. 1-5에서 Git으로 저장 시점을 남기는 법을 배우고, 드디어 1-6에서 AI한테 앱을 만들게 합니다. 1-7에서 주소를 붙여 세상에 내놓고, 1-8에서 돌아봅니다. 처음부터 끝까지 「미니 노션」이라는 예제 하나로 갑니다. 노션에서 블록 쌓아 글 쓰는 기능만 쏙 떼어 온 개인 메모장이에요. 저는 미니 노션을 만들고, 여러분은 같은 순서로 자기 아이디어를 만듭니다.

곁들일 이야기요리 수업이랑 비슷합니다. 강사가 앞에서 김치찌개를 한 번 끓여 보이면, 여러분은 같은 순서로 된장찌개를 끓이는 거죠. 레시피를 외우는 게 아니라 「순서」를 몸에 익히는 게 목표입니다.

4바이브코딩의 유래

「바이브코딩」, 말부터 좀 수상하죠. 코딩을 느낌으로 한다니요. 이 말은 2025년 2월에 Andrej Karpathy라는 사람이 X에 올린 글에서 처음 나왔습니다. 「느낌에 완전히 몸을 맡기고, AI의 빠른 발전을 받아들이고, 코드가 있다는 사실조차 잊는 방식」이라고 했어요. 이분은 2023년 1월에 이미 「가장 인기 있는 새 프로그래밍 언어는 영어」라고 말한 적도 있습니다. 그리고 2025년 11월, 영국 Collins 사전이 이 말을 올해의 단어로 뽑습니다. 트윗 하나가 1년도 안 돼 사전에 올라간 겁니다. 웬만한 신조어보다 출세가 빠르죠.

곁들일 이야기Karpathy는 OpenAI 창립 멤버이고, Tesla에서 자율주행 AI를 이끌었던 사람입니다. 그런 사람이 같은 글에 「오류 메시지가 나오면 설명 없이 그냥 복사해서 붙여 넣는다」고 썼어요. 그리고 이 방식은 주말에 만들고 버릴 프로젝트에 꽤 괜찮다고 했습니다. 처음부터 「가볍게 만들어 보는 방식」으로 나온 말이라는 것, 뒤에서 한계 이야기할 때 다시 써먹겠습니다.

5바이브코딩 사례

그래서 사람들이 진짜로 뭘 만들었냐. 개발자 Pieter Levels는 AI랑 같이 브라우저에서 바로 하는 3D 비행 게임 fly.pieter.com을 혼자 만들었습니다. Karpathy 본인은 식당 메뉴판 사진을 찍으면 메뉴마다 음식 그림을 보여 주는 MenuGen을 만들었고요. 외국 식당에서 메뉴판 보고 멍해져 본 분들은 이게 왜 필요한지 아실 겁니다. 우리가 1부에서 만들 미니 노션은 이것보다 훨씬 작은 업무 도구예요. 다만 하나만 기억해 두세요. 만드는 것과 남들이 쓰게 공개하는 것은 전혀 다른 일입니다. 이건 1-7에서 직접 겪어 봅니다.

곁들일 이야기Karpathy가 MenuGen 후기를 블로그에 남겼는데요, 자기 컴퓨터에서 돌아가게 만드는 건 금방이었는데 로그인 · 결제 · 배포 설정 붙이는 데 훨씬 오래 걸렸다고 합니다. AI 전문가도 거기서 시간을 쓴 겁니다. 슬라이드의 「배포는 별도 과정」이 바로 이 이야기입니다.

6원시인과 사과

자, 바이브코딩 얘기는 잠깐 접고, 애초에 코딩이 뭔지부터 보겠습니다. 컴퓨터를 사과를 처음 본 원시인이라고 생각해 보세요. 원시인은 이게 먹는 건지, 던지는 건지, 모자인지 모릅니다. 그래서 「집어 든다, 입에 가져간다, 깨문다」를 하나하나 알려 줘야 해요. 그리고 원시인은 알려 준 것만 정확히 그대로 합니다. 「깨문다」를 빼먹으면? 사과를 입에 댄 채로 영원히 서 있습니다. 이 할 일 목록이 바로 코드입니다.

곁들일 이야기프로그램 오류를 「버그」, 벌레라고 부르잖아요. 1947년 하버드 대학 Mark II 컴퓨터 안에 진짜 나방이 끼어서 고장 난 기록이 있습니다. 그 나방을 테이프로 붙여 둔 작업 일지가 지금 미국 스미스소니언 박물관에 있어요. 다만 「버그」라는 말 자체는 그 전부터 기술자들이 쓰던 말이니, 「나방 때문에 생긴 말」은 아니라는 것까지 알아 두시면 아는 척하기 좋습니다.

7코드의 저장과 실행

네 컷 만화로 보겠습니다. 첫 컷, 원시인이 사과 앞에서 멍하니 있습니다. 명령이 없으니 아무것도 못 해요. 두 번째 컷, 이름과 먹는 법을 알려 줍니다. 이게 코드를 써서 저장하는 일입니다. 세 번째 컷, 다음 사과를 보자마자 바로 먹습니다. 한 번 저장한 코드는 매번 똑같이 실행되거든요. 그런데 네 번째 컷, 배를 만나자 다시 얼어붙습니다. 코드에 「배」는 없었으니까요. 컴퓨터가 실행할 명령을 이렇게 프로그래밍 언어로 적는 일, 그게 코딩입니다.

곁들일 이야기엑셀 「매크로 기록」 써 보신 분? 한 번 기록해 두면 버튼 하나로 똑같이 반복되는데, 표에 열 하나만 끼워 넣어도 엉뚱한 칸을 신나게 고쳐 놓습니다. 그게 네 번째 컷의 배입니다.

8프로그래밍 언어의 발전

과거에는 원시인한테 말을 걸려면 원시인 말, 즉 프로그래밍 언어부터 배워야 했습니다. 다행히 그 말이 점점 사람 쪽으로 다가왔어요. 1940년대 말 어셈블리는 CPU한테 명령을 하나씩 시키는 방식이라, 덧셈 하나에도 칸에 값 넣고, 더하고를 따로 써야 했습니다. 요리로 치면 밭에서 파부터 뽑아 오는 단계예요. 1957년 FORTRAN, 1991년 Python 같은 고급 언어가 나오면서 영어 단어랑 수식으로 쓸 수 있게 됐습니다. 밀키트 단계죠. 그리고 2025년쯤부터는 「1부터 100까지 더해서 화면에 보여 줘」라고 우리말로 말하면 AI가 코드를 씁니다. 식당에서 주문만 하는 단계까지 온 겁니다. 같은 계산을 이 세 가지 말로 차례로 보겠습니다.

곁들일 이야기Python이라는 이름, 뱀인 줄 아셨죠? 영국 코미디 프로그램 「Monty Python's Flying Circus」에서 따온 이름이라고 Python 공식 문서에 적혀 있습니다. 만든 사람은 Guido van Rossum이고, FORTRAN은 IBM의 John Backus 팀이 만들었습니다.

9어셈블리어 코드

첫 번째, 컴퓨터에 제일 가까운 말 어셈블리어입니다. 계산은 「1부터 100까지 더해서 화면에 보여 주기」. 왼쪽이 이 강의 노트북에서 실제로 돌려 본 코드인데요, 38줄입니다. 네, 덧셈 하나에 38줄이요. x1, x2는 CPU 안의 작은 칸 이름입니다. 칸에 값 넣고, 더하고, 100이랑 비교하고, 아니면 위로 돌아가라. 이걸 한 줄씩 시킵니다. 압권은 화면에 글자 찍는 부분이에요. 5050을 한 글자씩 쪼개서 글자로 바꾼 다음, 운영체제한테 「4번 일 좀 해 주세요」라고 부탁합니다. 오른쪽 번호표에서 4번이 write, 화면에 쓰기예요. 숫자 하나 보여 주는 데 이렇게 공손해야 합니다.

곁들일 이야기1960~70년대 개발자들은 이런 코드를 종이에 적고, 구멍 뚫린 카드로 옮겨서 컴퓨터에 넣었습니다. 쉼표 하나 틀리면 다음 날 다시 줄 서야 했다는 이야기가 흔해요. 오타 하나에 하루가 날아가는 겁니다.

10고급 언어 코드 · Python

같은 계산, Python은 4줄입니다. 38줄이 4줄이 됐어요. 합계를 0으로 두고, 1부터 100까지 하나씩 더하고, 출력. for, range, print, 영어를 조금만 알면 대충 뜻이 짐작되죠. CPU 칸 고르기, 숫자를 글자로 바꾸기, 운영체제에 공손하게 4번 부탁하기, 이걸 전부 Python이 알아서 해 줍니다. 실행하면 결과는 똑같이 5050입니다.

곁들일 이야기수학자 가우스가 어릴 때 이 문제를 「1+100, 2+99 …」 이렇게 50쌍으로 묶어서 순식간에 풀었다는 일화가 있죠. 선생님이 시간 좀 벌려고 낸 문제였는데 말이죠. 이 계산이 코딩 첫 예제로 단골인 이유입니다.

11자연어 요청

그리고 바이브코딩. 「1부터 100까지 더한 값을 화면에 보여 줘」, 한 문장이면 끝입니다. Claude Code가 Python 코드를 직접 만들고 실행해서 5050이라고 알려 줍니다. 38줄, 4줄, 그리고 이제 0줄이에요. 이렇게 AI랑 말을 주고받으며 프로그램을 만드는 방식이 바이브코딩입니다. 그런데 사람이 할 일이 딱 하나 남습니다. 5050이 맞는 답인지 확인하는 일이요. 이 확인하는 눈이 오늘 계속 나올 주제입니다.

곁들일 이야기예를 들어 AI가 「1부터 100까지」를 「1부터 100 전까지」로 알아들으면 답은 4950이 됩니다. 그럴듯하죠? 숫자만 보고 「어, 이상한데」 할 수 있어야 코드를 안 읽고도 AI한테 일을 맡길 수 있습니다.

12AI 코딩 도구의 변화

AI 코딩 도구도 몇 년 사이에 많이 컸습니다. 2021년 GitHub Copilot은 자동완성이었어요. 사람이 코드를 쓰고 있으면 옆에서 「다음 줄 이거 아니에요?」 하고 슬쩍 제안하는 수준. 2022년 ChatGPT는 대화형입니다. 물어보면 코드를 써 주는데, 그걸 어디 붙이고 어떻게 실행할지는 사람 몫이었죠. 복사 붙여넣기 장인이 많이 탄생했습니다. 2025년 Claude Code 같은 위임형은 목표만 주면 파일을 찾고, 고치고, 실행해서 확인까지 합니다. 막대 길이는 측정값이 아니라, 사람 일과 AI 일의 비중을 대략 보여 주는 그림이에요. 대화형과 위임형 차이는 다음 1-2에서 직접 비교해 봅니다.

곁들일 이야기길 찾기로 치면 이렇습니다. 자동완성은 지도에 다음 갈림길만 형광펜으로 칠해 주는 친구, 대화형은 전화로 「거기서 좌회전」 알려 주는 친구, 위임형은 목적지만 말하면 운전해 주는 친구. 그래도 어디 갈지는 여전히 내가 정합니다.

13위임의 한계

운전해 주는 친구라도 목적지를 잘못 찍으면 엉뚱한 데 도착합니다. AI는 회사 밖에 공개된 것만 압니다. 로그인 화면, 할 일 목록처럼 세상에 예시가 널린 건 잘 만들어요. 그런데 우리 회사 규칙, 업무상 예외, 우리 팀 사람들 습관은 모릅니다. 이런 걸 비즈니스 로직이라고 합니다. 그래서 사람이 규칙을 정해 주고, AI가 만든 순서를 읽고, 빠진 곳을 짚어 줘야 해요. 그 순서를 읽는 눈, 그게 알고리즘입니다. 알고리즘이라니까 갑자기 어려워 보이죠? 농담 하나로 시작하겠습니다.

곁들일 이야기「휴가 신청 화면 만들어 줘」라고 하면 AI는 날짜 고르고 제출하는 화면을 뚝딱 만듭니다. 그런데 우리 팀은 3일 넘으면 팀장 결재가 하나 더 붙는다? 그건 내가 말 안 하면 AI가 알 방법이 없습니다. 독심술은 아직 없어요.

14우유 6통 사건

아내가 남편한테 부탁합니다. 「우유 하나 사 와. 아보카도 있으면 6개 사 와.」 남편이 의기양양하게 들고 온 건… 우유 6통입니다. 남편은 왜 그랬을까요? 남편 입장에서는 시킨 대로 정확히 한 겁니다. 잠깐 생각해 보시고, 다음 장에서 순서도로 범인을 잡아 보겠습니다.

곁들일 이야기원래는 개발자들 사이에서 「우유 한 통 사 와, 달걀 있으면 6개 사 와」로 오래 돌던 농담입니다. 개발자들이 이 농담을 유독 좋아하는 이유가 있어요. 매일 컴퓨터한테 이런 식으로 당하거든요.

15알고리즘

위쪽이 아내의 뜻입니다. 우유 1개 사고, 아보카도가 있으면 아보카도 6개 사고, 끝. 아래쪽이 남편의 해석입니다. 아보카도가 있는지 먼저 보고, 있으면 우유를 6개. 문장은 똑같은데 「있으면」이 어디에 붙느냐가 달라진 거죠. 이렇게 일을 푸는 순서 있는 절차를 알고리즘, 그걸 그림으로 그린 걸 순서도라고 합니다. 순서도 볼 때는 세 가지만 보세요. 뭘 먼저 하는지, 조건이 어디에 걸리는지, 언제 멈추는지. AI가 만든 결과를 볼 때도 딱 이 세 가지입니다.

곁들일 이야기회사에도 우유 6통 사건은 흔합니다. 「자료 정리해서 금요일까지, 가능하면 표로.」 금요일까지 못 하면 표로라도 내라는 건지, 표는 그냥 선택이라는 건지. 사람끼리도 헷갈리는 문장을 AI라고 안 헷갈릴 리가 없겠죠.

16라면 끓이기 알고리즘

이번엔 여러분이 순서도를 채워 볼 차례입니다. 종목은 국민 요리, 라면입니다. 물음표에 뭐가 들어갈지 잠깐 생각해 보세요. 물 550ml 붓고, 불 켜고. 그다음 「물이 끓었나?」를 물어봅니다. 아니면 1분 기다렸다가 다시 묻고, 끓었으면 면과 스프를 넣습니다. 이 위로 되돌아가는 화살표가 반복이에요. 4분 30초 끓이고 불 끄면 끝. 처리, 조건, 반복, 끝. 이 네 개만 보이면 여러분은 이제 순서도를 읽을 수 있습니다. 축하드립니다.

곁들일 이야기라면 봉지 뒷면에 「물이 끓으면 면과 스프를 넣으세요」라고는 쓰여 있어도, 「끓을 때까지 계속 쳐다보며 기다리세요」라고는 안 쓰여 있습니다. 사람은 당연히 아니까요. 원시인 컴퓨터는 그것까지 적어 줘야 합니다. 안 그러면 차가운 물에 면 넣고 4분 30초 기다립니다.

17로그인 순서도 · 피드백 전

자, 이 눈으로 AI가 만든 걸 한번 검사해 보겠습니다. 「이메일 로그인 만들어 줘」라고만 하면, AI는 이메일과 비밀번호를 받아서 맞으면 들어가고, 틀리면 다시 입력하게 하는 순서를 만듭니다. 세상에서 제일 흔한 로그인이죠. 그런데 순서도를 잘 보세요. gmail이든 naver든 아무 메일로 다 들어올 수 있고, 비밀번호는 백 번이고 천 번이고 다시 넣을 수 있습니다. AI가 잘못한 걸까요? 아니요. 우리 회사 사정을 몰랐을 뿐입니다.

곁들일 이야기비밀번호를 무한히 넣을 수 있으면, 프로그램을 돌려서 가능한 비밀번호를 하나씩 계속 넣어 보는 공격이 가능합니다. 은행 앱이 다섯 번 틀리면 잠가 버려서 짜증 났던 경험, 사실 그게 우리를 지켜 준 거예요.

18로그인 순서도 · 피드백 후

같은 요청에 규칙 두 줄만 더해 봅니다. 「회사 이메일만」, 「5번 틀리면 10분 잠금」. 그러면 순서도에 조건이 두 개 끼어듭니다. 회사 메일인지 먼저 보고 아니면 돌려보내고, 비밀번호가 틀리면 몇 번째인지 세다가 다섯 번째에 10분 잠급니다. 같은 AI인데 말 두 줄 차이로 개인 메일은 막히고 @company.com만 통과하고, 무한 대입도 막혔습니다. 이게 이 과정에서 말하는 알고리즘 읽기예요. 코드 한 줄 안 읽고, 순서도에서 빠진 조건을 찾아 한마디 해 준 겁니다.

곁들일 이야기이걸 보고 「잠긴 10분 동안 비밀번호 까먹은 사람은 어떡하지?」라는 생각이 드셨다면, 축하합니다. 방금 다음 피드백을 하신 겁니다. 이런 빈 곳은 개발자보다 그 업무를 매일 하는 사람이 더 잘 찾아요.

19사람과 AI의 역할

정리하면 역할이 깔끔하게 나뉩니다. 사람은 규칙을 정하고, AI가 만든 순서를 읽고, 빠진 조건과 예외를 짚어 줍니다. AI는 코드를 쓰고, 저장하고, 실행하고, 짚어 준 대로 고칩니다. 사람은 요청과 피드백을 보내고, AI는 코드와 결과를 돌려줍니다. 그런데 궁금하지 않으세요? AI는 대체 어떻게 코드를 쓰는 것도 모자라 실행까지 하는 걸까요. LLM, 도구, 에이전트 순서로 뚜껑을 열어 보겠습니다.

곁들일 이야기집 수리할 때를 떠올려 보세요. 콘센트가 어디에 필요한지는 거기 사는 집주인이 알고, 배선을 어떻게 하는지는 기사님이 압니다. 공사 끝나면 집주인이 콘센트마다 충전기 꽂아 보죠. 그 점검 목록이 나중에 배울 테스트 케이스입니다.

20LLM

먼저 LLM. Large Language Model, 대규모 언어 모델입니다. ChatGPT나 Claude의 두뇌 부분이에요. 이름을 쪼개 보면 뜻이 다 들어 있습니다. Large, 인터넷 글 · 책 · 코드를 엄청나게 많이 읽었다. Language, 다루는 게 글이다. 프로그래밍 언어도 글이니까 코드도 됩니다. Model, 다음에 올 글 조각을 골라 이어 쓰는 계산 프로그램이다. Claude, GPT, Gemini 다 LLM이에요. LLM이 하는 일은 의외로 단순합니다. 글을 토큰이라는 작은 조각으로 쪼개 읽고, 다음 조각을 이어 씁니다. 그래서 질문에 답도 쓰고 코드도 씁니다. 그런데 혼자서는 파일을 열지도, 저장하지도, 실행하지도, 화면을 보지도 못합니다. 말은 청산유수인데 손이 없어요.

곁들일 이야기세상 모든 책을 읽은 사람이 손이 묶인 채로 전화로만 이야기할 수 있다고 생각해 보세요. 「서랍 두 번째 칸 열고 파란 파일 꺼내세요」까지는 말해 줄 수 있는데, 직접 서랍을 열 수는 없는 거죠.

21도구가 필요한 이유

손이 없으면 뭐가 문제냐, 계산으로 직접 보겠습니다. 482,917 곱하기 739,264. 여섯 자리 곱셈이에요. 이걸 AI한테 도구 없이 바로 답하라고 해 보겠습니다. (화면에서 직접 질문) 자, 답이 나왔습니다. 그럴듯하죠? 오른쪽 정답, 357,003,153,088이랑 한 자리씩 맞춰 보세요. 어디가 다른지 눈으로 바로 찾을 수 있으세요? 쉽지 않습니다. 그래서 더 무섭습니다. LLM은 계산을 하는 게 아니라 그럴듯한 숫자를 이어 쓰는 거라서 그래요. 계산 도구가 있으면 얘기가 달라집니다. 모델은 「이건 계산기 불러야겠다」고 판단만 하고, 실제 곱셈은 도구가 합니다. 판단은 모델, 실행은 도구입니다.

곁들일 이야기시연에서 AI가 맞혔다면 「이번엔 맞혔네요, 그런데 매번 맞힐까요?」로 넘어가면 됩니다. 몇 번 다시 물으면 답이 달라지기도 합니다. 우리도 큰 수 곱셈은 암산 안 하고 휴대폰 계산기 켜잖아요. 일 잘하는 사람은 암산이 빠른 사람이 아니라, 계산기 꺼낼 타이밍을 아는 사람입니다.

22LLM과 코딩 에이전트

지금까지 본 걸 그림 세 컷으로 정리해 보겠습니다. 첫 컷, 두뇌만 있습니다. LLM이에요. 글을 읽고, 쓰고, 판단은 하는데 손이 없습니다. 아까 그 「말은 청산유수인데 손이 없는」 상태죠. 두 번째 컷, 두뇌가 도구를 쥐었습니다. 이제 파일을 읽고, 검색하고, 명령을 실행할 수 있어요. 방금 본 계산 도구가 바로 이겁니다. 세 번째 컷, 두뇌가 노트북 앞에 앉아서 일을 합니다. 도구로 작업하고, 결과를 확인하고, 또 고치고. 이걸 스스로 반복하는 단계가 코딩 에이전트입니다. 정리하면 에이전트는 판단하는 모델에 행동하는 도구를 붙인 것. Claude Code가 바로 이 세 번째 컷이에요. 이게 진짜 어떻게 돌아가는지, 회사 이야기로 한번 풀어 보겠습니다.

곁들일 이야기앞에서 말한 「손이 묶인 채 전화로만 말하는 박식한 사람」의 손을 풀어 주고 컴퓨터 앞에 앉힌 모습이 세 번째 컷입니다. 같은 사람이라도 직접 해 보고 결과를 눈으로 볼 수 있으면 일의 정확도가 달라지죠. 나중에 테스트 케이스를 주면 에이전트가 직접 돌려 보고 통과하는지 확인할 수 있는 것도 이 덕분입니다.

23경비 정산 비유

계산기 이야기를 회사 버전으로 늘려 보겠습니다. 월말에 팀장님이 「이번 달 경비 합계 좀 내 줘」 하십니다. 이게 사용자 요청이에요. 정산 담당자는 먼저 머리로 정합니다. 어느 영수증부터 볼까, 뭘 더할까. 이게 LLM의 판단입니다. 실제 더하기는 계산기로 하죠. 도구 실행입니다. 계산기 화면 숫자를 보고 다음 영수증으로 넘어가고, 또 두드리고. 도구 결과가 다시 다음 판단의 재료가 되는 겁니다. 영수증이 바닥나면 더 두드릴 게 없으니 합계를 보고합니다. 방금 본 세 번째 컷, 노트북 앞 두뇌가 일하는 방식이 정확히 이겁니다.

곁들일 이야기그런데 영수증 하나가 달러로 결제돼 있다면? 담당자는 환율 사이트를 열고 다시 계산기를 두드립니다. 처음 계획에 없던 도구도 상황 보고 꺼내 쓰는 것, 에이전트가 한 번에 끝내지 않고 빙글빙글 도는 이유가 이겁니다.

24에이전트 루프

이걸 그림으로 그리면 에이전트 루프입니다. 요청이 들어오면 하네스가, 그러니까 모델을 감싸고 있는 프로그램이 요청이랑 지금까지 결과를 모아서 모델한테 보냅니다. 모델이 다음 행동을 고릅니다. 도구가 필요하면 도구를 부르고, 하네스가 Glob으로 파일을 찾거나 Read로 읽거나 Write로 저장해서 그 결과를 붙여 다시 모델한테 보냅니다. 이걸 몇 바퀴 돌다가 모델이 「이제 도구 필요 없다」고 판단하면 사용자한테 답을 냅니다. 모델은 머리, 하네스는 손발. 이것만 기억하시면 됩니다.

곁들일 이야기내비게이션이 딱 이렇습니다. 현재 위치 받아서 경로 판단하고, 차가 움직이면 바뀐 위치로 또 판단하고. 우리가 골목으로 빠지면 「경로를 재탐색합니다」 하죠. 결과를 보고 다시 판단하는 고리, 그게 루프입니다.

25바이브코딩의 가능성과 한계

그럼 바이브코딩으로 뭘 만들 수 있고, 뭐는 아직 참아야 할까요. 화면 한두 개, 많아야 세 개짜리 웹 페이지, 할 일 목록이나 투표나 체크리스트는 잘 만듭니다. 계산기나 자료 정리 같은 업무 보조 도구, 「이런 거 있으면 좋겠어요」를 보여 주는 시제품도 좋아요. 반면 돈이나 개인정보를 다루는 서비스는 전문 보안 점검이 필요합니다. 동시에 많은 사람이 쓰는 서비스는 서버와 데이터베이스 설계가 필요하고요. 아무도 코드를 안 들여다본 채로 운영하다가 장애가 나면, 원인 찾다가 밤샙니다.

곁들일 이야기팀 회식 장소 투표 페이지는 오늘 오후에 만들어서 써도 됩니다. 잘못돼 봐야 삼겹살 대신 회 먹는 정도니까요. 하지만 팀원 연봉이나 주민등록번호를 받는 페이지는 바이브코딩만으로 만들어 공개하면 안 됩니다. 「틀려도 다시 만들면 되는 것」부터 시작하세요.

26요청과 결과

마지막 질문입니다. 「미니 노션 만들어 줘」, 이 한 줄만 던지면 어떻게 될까요? AI는 성실하게 파일 읽고, 코드 쓰고, 실행해서 확인하고 화면을 하나 내놓습니다. 화면은 나와요. 문제는 그게 내 머릿속 미니 노션이랑 같냐는 거죠. 페이지를 지울 수 있는지, 새로 고침해도 글이 남는지, 「/」 메뉴가 있는지, 요청에 없었으니 전부 AI 마음대로입니다. 1부 전체가 이 차이를 줄이는 방법이에요. 1-8 회고에서 이 질문을 다시 꺼내 보겠습니다. 그 전에 1-2에서 연장부터 챙기러 가죠.

곁들일 이야기인테리어 맡기면서 「예쁘게 해 주세요」만 하면 어떻게 될까요. 사장님 취향의 예쁨이 나옵니다. 그래서 도면을 먼저 그리고, 공정마다 사진 받아 보고, 끝나면 하자 점검을 하죠. 1부의 기획서, 개발 계획, Git, 작은 요청, 공개 전 점검이 각각 이 단계입니다.

곁들일 이야기가게를 하나 연다고 해 보죠. 상담부터 공사까지 한 번에 해 주는 시공사(Claude Code), 설계도랑 공사 기록 넣어 둘 창고(GitHub), 손님이 찾아올 간판과 주소(Vercel). 상담 따로, 공사 따로 맡기면 같은 설명을 두 번 해야 하잖아요.

31Claude와 Claude Code

그럼 왜 굳이 Claude Code일까요. 이름이 거의 똑같은 Claude 대화창도 있는데요. 1-1 「AI 코딩 도구의 변화」에서 본 대화형과 위임형 차이입니다. 「미니 노션 만들어 줘」, 같은 요청을 두 도구에 똑같이 해 보겠습니다. 위쪽 Claude는 코드를 글로 답해 줍니다. 그다음부터는 사람 일이에요. 코드 복사하고, 파일 만들어 붙여 넣고, 저장해서 브라우저로 열고, 오류 나면 다시 물어보고. 사람 손이 네 번 갑니다. 아래쪽 Claude Code는 폴더 파일을 직접 읽고, index.html을 만들고, 실행해서 확인하고, 오류도 알아서 고칩니다. 사람은 마지막에 결과만 봐요. 차이는 딱 하나, 내 컴퓨터 파일에 AI 손이 닿느냐입니다. 그래서 이 강의는 처음부터 끝까지 Claude Code 하나로 갑니다.

곁들일 이야기예를 들어 전화로 요리법을 듣는 것과, 요리사가 우리 집 부엌에 와서 직접 해 주는 것의 차이예요. 전화로는 아무리 친절하게 알려 줘도 양파는 내가 썰어야 합니다.
곁들일 이야기엑셀 수식을 챗봇에 물어보고, 복사해서 셀에 붙였더니 오류, 다시 묻고 또 붙이고. 해 보신 분 많으시죠? 위쪽 줄이 바로 그 과정입니다.

32Claude Code 사용 환경

Claude Code는 쓰는 곳이 여러 군데입니다. 검은 명령어 창, 터미널에서 쓰는 방식이 기능이 제일 많고요. VS Code 같은 편집기에서는 확장 프로그램으로, JetBrains 편집기에서는 플러그인으로 씁니다. macOS랑 Windows용 데스크톱 앱도 있고, claude.ai/code에서 웹으로 클라우드에서 돌릴 수도 있어요. 어디서 쓰든 안에서 도는 엔진과 설정은 같습니다. 이 강의는 파일을 눈으로 보면서 작업할 수 있는 VS Code를 기본으로 갑니다. 검은 창이 무서우신 분들, 안심하셔도 됩니다.

곁들일 이야기카카오톡을 휴대폰에서 쓰든 PC에서 쓰든 같은 계정, 같은 대화방이 보이잖아요. 화면 모양만 다르고 안에 있는 건 똑같습니다.

33VS Code

VS Code 화면은 네 구역입니다. 왼쪽 ① 탐색기는 폴더 안 파일 목록, 가운데 ② 편집기는 파일 내용. 아래 ③ 터미널은 명령어 치는 창이고, 오른쪽 ④가 Claude Code랑 대화하는 패널이에요. 여러분은 주로 ④에서 말을 걸고, ①과 ②에서 뭐가 바뀌었는지 확인하게 됩니다. 말은 오른쪽에서, 감시는 왼쪽에서. 이렇게 기억하시면 됩니다.

곁들일 이야기윈도우 탐색기나 맥 Finder로 폴더를 열어 두고, 옆에 메모장 띄우고, 또 옆에 메신저 창 하나 더 열어 둔 모습을 한 화면에 모았다고 보시면 돼요.
곁들일 이야기VS Code는 Microsoft가 무료로 배포하는 편집기입니다. 개발자들이 가장 많이 쓰는 편집기 가운데 하나라서, 막혔을 때 검색하면 자료가 금방 나옵니다.

34확장 프로그램

VS Code는 처음 깔면 기본 기능만 있고, 필요한 건 확장 프로그램으로 붙입니다. 휴대폰으로 치면 VS Code가 휴대폰, Marketplace가 앱 스토어, 확장 프로그램이 앱이에요. 순서도 같습니다. ① 검색창에 이름 치고, ② 목록에서 고르고, ③ Install 누르고. 앱 깔아 보신 분이면 이미 다 아시는 겁니다.

곁들일 이야기크롬에 번역이나 광고 차단 기능을 확장 프로그램으로 붙여 보신 분? 그분들은 사실상 오늘 실습 하나를 미리 하신 겁니다.

그럼 이런 생각 드실 거예요. 기획서 그냥 Claude Code한테 주면 안 돼요? 왼쪽이 우리 기획서입니다. 선택지로 고른 내 말이죠. 무엇을 하고 싶은지, 왜인지, 어떻게 확인하는지는 다 있습니다. 그런데 어떻게 만들지는 없어요. 그건 우리 일이 아니었으니까요. 오른쪽이 개발자가 정해야 하는 것들입니다. 어디에 저장할지, 무엇부터 만들지, 어떤 기술과 파일로 만들지, 한 번에 다 만들지. 이걸 안 정하고 시키면 Claude Code는 묻지 않고 추측합니다. 서버를 새로 만들고, 순서도 마음대로, 전부 한꺼번에. 빨간 칸은 예시예요. 그래서 개발 계획이 필요합니다. 다행인 건, 이건 우리가 쓰는 게 아니라 AI 개발자가 씁니다. 우리는 읽고 확인만 해요.

곁들일 이야기식당에서 「매콤한 걸로, 둘이 먹을 만큼」은 손님이 정하고, 불 세기랑 조리 순서는 주방이 정하죠. 손님이 주방 일까지 알 필요는 없습니다. 다만 나온 음식이 주문대로인지는 손님이 확인해야죠.

77조감도와 설계 도면

집 짓기로 보겠습니다. 조감도는 어떤 집인지, 왜 좋은지 보여 주는 그림이죠. 우리 기획서가 이 조감도예요. 내가 씁니다. 설계 도면은 방 크기, 배관, 재료가 적힌 전문 문서입니다. 앱에서는 개발 계획이고, 건축가 대신 AI 개발자가 씁니다. 집주인은 도면을 다 읽을 줄 몰라도 되지만, 건축가한테 「이 도면대로면 거실이 어디고 창문이 몇 개예요?」라고 설명은 듣죠. 그게 쉬운 말 요약입니다. 그리고 다 지은 뒤 준공 검사는 완료 기준, 우리가 1-3에서 쓴 확인 문장이 그대로 들어갑니다.

곁들일 이야기인테리어 맡겨 보신 분은 아실 거예요. 도면을 받으면 다 이해하는 척하기보다 「이건 뭐예요?」라고 물어보는 게 나중에 공사 다시 하는 것보다 훨씬 쌉니다.

78개발 리더 페르소나

이번엔 개발 리더 역할 메모를 만듭니다. 1-3에서 기획자.md를 만들었던 것처럼, 옆에 개발리더.md를 하나 더 만들어요. 그냥 개발자가 아니라 개발 리더예요. 회사에서 기획자랑 개발팀 사이에서 말을 옮겨 주는 사람이죠. 첫 줄이 핵심입니다. 「IT를 모르는 사람도 알 수 있게 쉬운 말로 묻고 계획을 쓴다.」 1-3 기획자.md 첫 줄과 같은 모양이죠. 둘째 줄, 전문 용어를 쓰면 바로 뜻을 풀어 준다. 셋째 줄, 정해지지 않은 건 선택지로 묻고 추천과 이유를 붙인다. 넷째 줄은 계획 단계에서 코드 쓰지 않기. 마지막 줄은 개발계획.md 칸인데, 맨 끝에 쉬운 말 요약이 들어 있어요. 이 여섯 줄이면 개발을 몰라도 대화가 됩니다.

곁들일 이야기1-3 처음에 본 조직도 기억나시죠. 개발 팀에서 기획 팀과 제일 많이 대화하는 사람이 개발 리드입니다. 같은 내용도 듣는 사람에 맞춰 바꿔 말하는 게 그 사람 일이에요.

79개발 계획 대화 예시

실제 대화는 이 정도예요. 「개발리더.md 대로 기획서.md를 읽고 개발 계획을 세워 줘.」 그러면 기획서에 없는 것 하나를 먼저 물어 옵니다. 쓴 내용을 어디에 보관할지, A와 B 선택지에 추천과 이유까지. 저는 A만 답했어요. 그러면 계획을 여섯 단계로 세우고, 단계마다 끝나면 화면에서 볼 것을 적었다고, 맨 끝 쉬운 말 요약부터 읽으면 된다고 알려 줍니다. 제가 「쉽게 말해 줘」라고 한 번도 안 했는데도요. 페르소나 없이 물으면 「localStorage로 persist할까요, DB로 할까요?」 같은 질문이 나옵니다. 개발리더.md 첫 줄 하나로 이만큼 달라집니다.

80화면 나누기

AI 개발자가 제일 먼저 하는 일 하나를 보여 드릴게요. 기획서의 화면 한 줄을 칸으로 나눕니다. 왼쪽 위가 기획서의 화면 칸이에요. 오른쪽 그림에서 칸이 하나씩 나타나죠. 왼쪽 회색 칸이 페이지 목록, F1. 오른쪽 위 안내 줄과 페이지 삭제 버튼. 큰 제목. 블록 줄이 쌓이는 칸, F2. 줄마다 왼쪽 점 여섯 개 손잡이가 F4. 그리고 /를 치면 뜨는 메뉴, F3. 마지막 F5 저장은 화면에 안 보이고 브라우저 안에서 일합니다. F 번호는 개발 계획에서 기능마다 붙이는 번호예요. 외울 필요는 없고, 「안내 줄 글씨를 키워 줘」처럼 칸 이름으로 콕 집어 말할 수 있게 됐다는 것만 기억하세요.

81쉬운 말 요약

개발 계획 원문은 왼쪽처럼 생겼습니다. F3, localStorage, T4. 비개발자가 읽기엔 외계어죠. 화면에서도 점점 흐려집니다. 그런데 개발 리더는 계획 끝에 오른쪽 같은 요약을 알아서 붙여 줍니다. 화면이 바뀌는 순서대로 여섯 줄. 왼쪽에 페이지 목록이 생기고, 오른쪽에 글과 체크 상자를 쓰고, 빈 줄에 /를 치면 메뉴가 뜨고, 손잡이로 순서를 바꾸고, 새로고침해도 남고, 휴대폰 폭에서도 잘 보이는지 확인. 이건 읽을 수 있죠? 우리가 볼 건 원문이 아니라 이 요약입니다. 개발리더.md 마지막 줄 칸에 「쉬운 말 요약」을 넣어 둔 덕분이에요.

82개발 계획 검토

요약을 읽을 때는 질문 세 개만 던집니다. 첫째, 내가 고른 기능이 다 들어 있나. 기획서 기능 칸에서 끌어 옮기기를 골랐죠. 요약 4번에 있으면 통과. 둘째, 모르는 단어가 있나. 있으면 그 자리에서 물어보세요. 「localStorage가 뭐야?」 「이 브라우저 안의 저장 공간」. 모르는 채로 넘어가는 게 제일 위험합니다. 셋째, 단계마다 화면에서 무엇을 보면 되나. 3번이 끝나면 빈 줄에 /를 쳐서 메뉴가 뜨는지 보면 되겠죠. 하나라도 「아니요」면 그 부분만 다시 요청합니다. 「요약 3번을 더 쉽게 설명해 줘」처럼요.

곁들일 이야기계약서를 다 이해하는 사람은 드물죠. 그래도 「이 조항이 무슨 뜻이에요?」라고 묻는 사람과 그냥 도장 찍는 사람은 결과가 다릅니다. 개발 계획도 마찬가지예요.

83실습 1-4 기획서로 개발 계획 세우기

자, 직접 해 볼 시간입니다. 입력은 1-3에서 만든 기획서.md, 산출물은 개발계획.md. 그 사이에 개발 리더 페르소나, 선택지 고르기, 검토 질문 세 개가 있습니다.

84실습 1-4 순서

네 단계입니다. 개발리더.md를 만들고, Plan으로 바꿔서 「개발리더.md 대로 기획서.md를 읽고 개발 계획 세워 줘」라고 요청합니다. 선택지가 오면 추천과 이유를 읽고 고르세요. 그래도 모르겠으면 「쉽게 다시 설명해 줘」. 계획이 나오면 끝의 쉬운 말 요약으로 검토 질문 세 개를 던지고, 고칠 점을 피드백한 뒤 승인해서 저장합니다. 어려운 말이 섞여 나오면 참지 말고 바로 「○○가 뭐야?」. 계획이 너무 길면 「태스크를 여섯 개 안으로 줄여 줘」라고 하세요.

85실습 1-4 · 1단계 개발리더.md 만들기

기획자.md 옆에 개발리더.md를 새로 만들고 화면의 여섯 줄을 씁니다. 말투는 바꿔도 되지만 첫 두 줄, 「IT를 모르는 사람도 알 수 있게」와 「전문 용어는 바로 뜻 풀이」는 꼭 남기세요. 그리고 저장.

86실습 1-4 · 2단계 Plan Mode 요청 · 선택지

1-3과 똑같이 모드 표시를 Plan으로 바꾸고, 「개발리더.md 대로 기획서.md를 읽고 개발 계획 세워 줘」라고 합니다. 그러면 기획서에 없던 것들을 쉬운 말 선택지로 물어봐요. 데이터를 어디 저장할지, 무슨 기술로 만들지. 추천과 이유를 읽고 고르세요. 둘 차이를 모르겠으면 「A와 B 차이를 쉽게 설명해 줘」. Recommended가 붙어 있다고 늘 정답은 아니에요.

87실습 1-4 · 3단계 쉬운 말 요약 검토

계획이 나오면 맨 끝 쉬운 말 요약부터 읽습니다. 화면처럼 화면이 바뀌는 순서로 적혀 있어요. 여기서 검토 질문 세 개. 고른 기능이 다 있나, 모르는 단어가 있나, 단계마다 볼 화면이 있나. 요약이 없거나 어렵게 나왔으면 「개발리더.md 대로 쉬운 말 요약을 붙여 줘」라고 하세요.

88실습 1-4 · 4단계 계획에 피드백

고칠 게 있으면 바로 승인하지 말고 승인 대신 고칠 점을 입력합니다. 화면의 예처럼 빠진 기능을 넣어 달라거나, 이름을 더 쉬운 말로 바꿔 달라거나. 그러면 계획을 고쳐서 다시 승인을 묻습니다. 계획 단계에서 한 번 고치는 게 코드 고치는 열 번보다 쌉니다. 마음에 들면 승인하세요. 개발계획.md가 저장됩니다.

89실습 1-4 확인

마지막으로 네 가지를 확인합니다. 내가 고른 기능이 다 들어 있나. 질문과 설명을 다 알아들었나. 단계마다 볼 화면이 요약에 적혀 있나. 저장 위치를 내가 직접 골랐나. 「아니요」가 있으면 그 부분만 다시 요청하고, 넷 다 「예」면 끝입니다. 1-5에서는 기획서랑 개발 계획을 Git으로 처음 커밋하고, 1-6에서 드디어 이 순서대로 개발합니다. 그때 하나씩 눌러 볼 목록이 바로 1-3에서 쓴 확인 문장이에요.

1-5 Git · GitHub 기초덱에서 보기

901-4 산출물 → 1-5

1-4에서 개발계획.md까지 만들었습니다. 이제 내 폴더에 문서가 두 개 있죠. 기획서.md랑 개발계획.md. 다음 단원부터는 이 폴더에 진짜 앱 코드가 들어옵니다. 그런데 그 전에 딱 하나만 먼저 해 두겠습니다. 폴더가 어떻게 바뀌는지 기록하는 장치, Git을 켜고 첫 커밋을 남기는 일이에요.

곁들일 이야기이사 가기 전에 짐 사진 찍어 두는 것과 비슷합니다. 아무 일 없으면 볼 일도 없어요. 그런데 뭐가 없어지거나 망가졌을 때, 「원래 이랬어요」 하고 내밀 근거가 됩니다.

91Git · GitHub 기초

1-5 단원, Git과 GitHub 기초입니다. 이름만 들으면 개발자 전용 같죠. 걱정 마세요, 이번에도 코드를 직접 치는 단원이 아닙니다. AI가 고친 걸 안전하게 저장하고, 필요하면 되돌리는 방법을 익히는 단원이에요.

921부 커리큘럼

전체 흐름으로 보면 다섯 번째 칸입니다. 1-1부터 1-4까지는 뭘 만들지 정했고, 1-6부터는 실제로 만들고 배포합니다. 1-5는 그 사이에서 작업 기록을 남기는 습관을 붙이는 단계예요. 공통 예제 미니 노션도 똑같이 첫 커밋부터 시작합니다.

곁들일 이야기바이브코딩에서는 AI가 한 번에 파일 여러 개를 고칩니다. 내가 손으로 고칠 때는 어디 고쳤는지 대충 기억이라도 나는데, AI가 고치면 그것도 없죠. 그래서 「어디가 바뀌었나, 원래대로 돌릴 수 있나」가 훨씬 중요해집니다. 이 단원을 코드 작성보다 먼저 두는 이유예요.

93파일 이름 버전 관리

먼저 다들 겪어 본 장면부터요. 발표자료 하나 고치다 보면 _v2, _최종, _최종_수정, _진짜최종, _진짜진짜마지막까지 사본이 늘어납니다. 보면서 웃으시는 분들, 다 압니다. 그 폴더 있으시죠. 이렇게 관리하면 세 가지가 어렵습니다. 어느 게 최신인지 날짜나 내용을 열어 봐야 알고, 뭐가 바뀌었는지는 두 파일을 나란히 놓고 눈으로 비교해야 하고, 중간 사본을 지웠으면 그 상태로는 다시 못 돌아갑니다. Git이 바로 이 문제를 푸는 도구입니다.

곁들일 이야기팀장님이 「사흘 전 버전에 있던 표 다시 살려 주세요」 하시면, 사본 여섯 개를 하나씩 열어서 표 있는 파일을 찾아야 합니다. 구글 문서나 워드의 「버전 기록」 기능이 이 수고를 줄이려고 나온 거고, Git은 같은 일을 폴더 전체 단위로 해 줍니다.

94세이브 포인트

Git을 이해하는 제일 쉬운 방법은 게임의 세이브 포인트입니다. 보스 방 앞에서 저장해 두면, 져도 그 지점부터 다시 시작하죠. 처음부터 다시 하라고 하면 게임기 던지고 싶어집니다. Git에서 저장하는 일을 커밋, 저장 슬롯에 붙이는 이름을 커밋 메시지라고 합니다. 저장 목록은 기록, log고요, 저장 시점을 불러오는 게 되돌리기입니다. 그리고 게임 클라우드 저장처럼 기록을 인터넷에 올려 두는 곳이 GitHub입니다.

곁들일 이야기게임기를 바꿔도 클라우드 저장 덕분에 이어서 할 수 있잖아요. GitHub에 올려 둔 기록도 마찬가지로, 노트북이 고장 나도 다른 컴퓨터에서 그대로 받아서 이어 작업할 수 있습니다.

95커밋 구성

커밋 하나를 뜯어 보겠습니다. 왼쪽은 이 커밋을 남긴 순간의 화면이에요. 로그인 버튼이 막 생겼죠. 오른쪽이 그 순간을 저장한 커밋 한 개입니다. 위에서부터 고유 번호 8fcbe80, 커밋마다 다르게 붙는 번호라 해시라고 부릅니다. 메시지 「버튼 추가」, 나중에 돌아갈 시점을 찾는 이름표예요. 시각과 작성자, 언제 누가 했는지. 작성자는 조금 뒤 실습에서 등록할 내 이름이 들어갑니다. 마지막이 바뀐 내용, index.html에 버튼 한 줄이 더해졌다는 기록이에요. 이 중에서 사람이 신경 쓸 건 메시지 하나입니다. 나머지는 Git이 알아서 채웁니다.

곁들일 이야기메시지를 전부 「수정」이라고만 남기면 어떻게 될까요. 기록이 스무 개 쌓였을 때 「수정, 수정, 수정…」 중에 어디로 돌아갈지 알 수가 없습니다. 파일 이름 「진짜최종」이랑 다를 게 없죠. 「로그인 버튼 추가」처럼 뭘 바꿨는지 한 줄이면 충분합니다.

96커밋 기록 쌓기

커밋은 이렇게 아래에서 위로 쌓입니다. 첫 화면 완성, 버튼 추가, 색상 수정, 이 순서로 세 번 저장했어요. 오른쪽은 같은 기록을 터미널에서 git log --oneline으로 본 모습인데, 최신 커밋이 맨 위에 나옵니다. 앞에 붙은 문자 일곱 개가 방금 말씀드린 고유 번호예요.

곁들일 이야기카톡 대화방을 위로 쭉 올려 보면 언제 무슨 말이 오갔는지 다 남아 있죠. 비슷합니다. 다만 Git 기록은 「뭘 바꿨는지」만 모아 둔 대화방이에요. 잡담은 없습니다.

97커밋으로 되돌리기

커밋이 왜 좋은지 화면으로 보겠습니다. v1 첫 화면 완성, v2 버튼 추가, v3 색상 수정. 커밋마다 그 순간의 화면이 통째로 저장돼 있어요. 그다음에 뭔가를 고쳤는데 화면이 깨졌습니다. 아직 커밋은 안 했고요. 이럴 때 「마지막 커밋으로 되돌려 줘」 한마디면, 화면이 v3 색상 수정 상태로 돌아옵니다. 사라지는 건 커밋 전에 한 실수뿐이에요. 게임에서 보스한테 지면 마지막 세이브 포인트에서 다시 시작하는 것과 똑같습니다. 그래서 잘 될 때마다 커밋, 이게 1-6에서 계속 반복할 습관입니다.

98Git과 GitHub

이제 GitHub입니다. 왼쪽 점선이 내 컴퓨터예요. Git은 여기서 기록을 만드는 프로그램입니다. 방금 v3 커밋을 새로 남겼죠. 그런데 이 기록은 아직 내 컴퓨터에만 있습니다. 노트북에 커피 쏟으면 같이 날아가요. 그래서 git push, 올리기를 합니다. 그러면 v3이 가운데 GitHub로 복사돼요. GitHub는 인터넷에서 이 기록을 보관해 주는 서비스입니다. 일단 GitHub에 올라가면 다른 컴퓨터에서 같은 기록을 받아 이어서 작업할 수 있고, 이걸 git pull, 받아 오기라고 합니다. 그리고 1-7에서 배울 Vercel도 GitHub에 있는 기록을 가져가서 배포해요. 아래 비유처럼 생각하시면 쉽습니다. Git은 휴대폰 사진첩, GitHub는 클라우드 백업, push는 백업 올리기, pull은 다른 기기에서 받기. Free 요금제로도 비공개 저장소를 개수 제한 없이 만들 수 있습니다.

곁들일 이야기Git이랑 GitHub, 이름이 비슷해서 같은 걸로 많이들 헷갈립니다. Git은 프로그램 이름이고, GitHub는 그 기록을 맡아 주는 서비스 이름이에요. 참고로 GitHub는 2018년에 마이크로소프트가 인수했습니다.

99Git 작업 흐름

실제로 기록이 어떻게 움직이는지 애니메이션으로 보겠습니다. 작업 폴더에서 파일을 고치면, git add로 커밋할 파일을 스테이징 영역에 담습니다. 그다음 git commit으로 로컬 저장소에 기록을 남기고, git push로 그 기록을 GitHub에 올려요. 반대로 다른 컴퓨터에서 올린 「문구 수정」 같은 새 커밋은 git pull로 받아서 내 폴더에 합칩니다. 왼쪽 세 칸이 내 컴퓨터, 오른쪽 한 칸이 인터넷입니다.

곁들일 이야기온라인 쇼핑으로 치면 이렇습니다. 작업 폴더는 매장 구경, git add는 장바구니 담기, git commit은 결제, git push는 택배 발송. 장바구니가 있으니까 고친 파일 중에 일부만 골라서 한 번에 저장할 수 있어요. 보기만 하고 안 사는 것도 자유고요.

100Git 작업 요청

add, commit, push, 명령어 이름이 꽤 나왔는데 외우실 필요 없습니다. 시험 안 봐요. 바이브코딩에서는 Claude Code한테 말로 시킵니다. 「지금 상태 커밋해 줘」 하면 git add랑 git commit이 실행되고 메시지도 Claude가 씁니다. 「커밋 기록 보여 줘」는 git log, 되돌리기는 두 가지예요. 아직 커밋 전이면 「방금 고친 거 취소해 줘」, git restore. 이미 커밋했으면 「마지막 커밋 되돌려 줘」, git revert인데, 이건 기록을 지우지 않고 「되돌림」이라는 새 커밋을 하나 더 남깁니다. 명령 실행은 Claude Code가 하고, 사람은 결과가 맞는지만 확인합니다.

곁들일 이야기엑셀 함수 이름을 몰라도 「합계 내 줘」 하면 되는 것과 비슷합니다. 다만 이름을 한 번 들어 둔 덕분에, Claude가 「git revert를 실행했습니다」라고 답할 때 무슨 일이 일어났는지 알아들을 수 있죠. 그 정도면 충분합니다.

101커밋 시점

그럼 언제 커밋하느냐. 기준은 세 가지입니다. 「로그인 버튼 동작」처럼 기능 하나가 됐을 때. 디자인을 갈아엎는 것처럼 크게 바꾸기 전. 그리고 브라우저로 보고 이상 없다는 확인이 끝났을 때. 흐름으로 보면 요청하고, 확인하고, 커밋하고, 다음 요청. 이 고리를 1-6에서 태스크마다 반복합니다.

곁들일 이야기예를 들어 AI한테 「전체 색상 바꿔 줘」 했는데 결과가 영 이상하게 나왔다고 해 보죠. 바로 앞에 커밋해 뒀다면 「방금 고친 거 취소해 줘」 한마디로 돌아갑니다. 안 해 뒀다면? 원래 모습이 뭐였는지부터 기억을 더듬어야 합니다. 보통 기억 안 납니다.

102Git 준비

실습 전에 준비할 게 있습니다. Git으로 기록하고 GitHub에 올리려면 네 가지가 필요해요. Git 설치, GitHub 계정, 작성자 등록, GitHub 로그인. GitHub 계정은 1-2에서 만들었죠. Git은 없으면 Claude Code에 「Git 설치해 줘」라고 하면 됩니다. 나머지 둘이 이번에 새로 하는 겁니다. 작성자는 커밋에 남는 「누가」이고, 로그인은 GitHub에 올릴 때 필요해요. 둘 다 처음 한 번만 하면 다음부터는 알아서 됩니다.

103Git 작성자 등록

아까 커밋 구성에 「누가」 칸이 있었죠. 그 칸을 채우는 게 작성자 등록입니다. 이름과 이메일을 이 컴퓨터에 한 번 적어 두면, 그다음 커밋부터 자동으로 들어가요. 값은 GitHub 가입할 때 쓴 이름과 이메일로 하세요. 그래야 GitHub에서 커밋이 내 계정과 연결돼 보입니다. 명령은 화면 같은 git config인데, 직접 칠 필요 없이 「Git 작성자를 내 GitHub 이름 · 이메일로 등록해 줘」라고 하면 Claude Code가 이름과 이메일을 묻고 실행합니다.

104GitHub CLI (gh)

GitHub 로그인에 쓰는 도구가 GitHub CLI, 줄여서 gh입니다. GitHub가 공식으로 만든 명령 도구예요. 웹사이트에서 버튼 눌러 하던 저장소 만들기, 올리기를 명령으로 할 수 있게 해 줍니다. 명령은 Claude Code가 실행하니까 외울 필요 없습니다. 우리가 할 일은 처음 한 번 설치하고 로그인해 두는 것뿐이에요. 설치도 Claude Code에 「GitHub CLI 설치해 줘」라고 하면 됩니다. 맥이면 brew, 윈도우면 winget 명령을 보여 주면서 허용할지 물어볼 거예요. 윈도우는 설치 뒤에 VS Code를 한 번 껐다 켜야 gh를 알아봅니다.

곁들일 이야기새 프로그램을 깔았는데 아이콘이 안 보여서 재부팅하니까 보였던 경험, 한 번쯤 있으시죠. VS Code도 비슷합니다. 이미 열려 있던 창은 설치 전 상태를 기억하고 있어요. 다시 열어야 새로 깐 도구를 알아봅니다.

105gh 로그인

설치했으면 gh를 내 GitHub 계정이랑 연결합니다. 이게 「브라우저 로그인 연동」이에요. 1-7에서 GitHub에 올릴 때 이 연결을 씁니다. Claude Code에 「GitHub 로그인 도와줘」라고 하면 로그인 명령을 실행하고, 화면에 짧은 코드를 보여 주면서 브라우저를 열어 줍니다. 브라우저에 그 코드를 넣고 승인하면 연결 끝이에요. 「로그인됐는지 확인해 줘」라고 하면 확인까지 해 줍니다. 혹시 여기서 멈춰 있으면 손 들어 주세요. 같이 하겠습니다. 여기서 중요한 게 하나 있습니다. 브라우저 승인은 반드시 사람이 직접 합니다. 비밀번호를 Claude한테 알려 주지 않아요. Claude는 연결된 권한으로 명령만 실행합니다.

곁들일 이야기거실 TV에서 넷플릭스나 유튜브 로그인할 때, TV에 뜬 코드를 휴대폰에 입력해 보셨죠? gh auth login도 같은 방식입니다. 리모컨으로 비밀번호 한 글자씩 치는 고행 대신, 이미 로그인된 휴대폰이나 브라우저에서 「이 기기 허락」만 누르는 겁니다.

115HTML과 프로그래밍 언어

116웹의 3요소

웹 화면이 무엇으로 이루어지는지 보겠습니다. 웹의 3요소, HTML · CSS · JS입니다. 같은 미니 노션 화면이 하나씩 더해질 때 어떻게 바뀌는지 보세요. 왼쪽은 HTML만 있을 때. 글자, 목록, 버튼, 내용은 다 있는데 모양이 없어요. 이게 뼈대입니다. 가운데는 CSS를 더한 화면. 왼쪽에 회색 페이지 목록, 오른쪽에 큰 제목. 모양과 배치, 색을 맡습니다. 오른쪽은 JS까지 더한 화면. 여기서 직접 눌러 보겠습니다. 가운데 CSS 칸의 「+ 새 페이지」를 클릭하면, 버튼이 흔들리기만 하고 아무 일도 안 생깁니다. 모양은 있는데 누르면 무슨 일을 할지 적힌 코드가 없거든요. 이제 오른쪽 JS 칸의 같은 버튼을 클릭해 볼게요. 이렇게 사용자가 누르거나 입력하는 걸 이벤트라고 합니다. 클릭 이벤트가 생기면 아래 app.js에서 onclick 줄부터 한 줄씩 불이 켜져요. 새 페이지를 목록에 넣고, 저장하고, 목록을 다시 그립니다. 그래서 목록에 「제목 없음」이 생기죠. 한 번 더 누르면 또 생기고, 목록을 누르면 그 페이지로 바뀝니다. 똑같이 생긴 버튼인데 JS가 있느냐 없느냐로 갈리는 겁니다. 누르면 무슨 일이 생기는지가 JS예요. 아래 검은 칸은 예시 앱의 실제 파일 조각입니다. index.html, style.css, app.js. 코드는 읽을 줄 몰라도 됩니다. 「색만 바꿔 줘」는 CSS, 「버튼 눌러도 안 돼」는 JS 쪽 문제라는 것만 기억하세요.

곁들일 이야기집으로 치면 HTML은 골조, CSS는 벽지와 조명 같은 인테리어, JS는 스위치를 누르면 불이 켜지게 하는 전기 배선입니다.

117브라우저로 열기

이 세 파일을 화면으로 보는 방법은 간단합니다. 점선 상자가 내 컴퓨터예요. ① 폴더에서 index.html을 더블클릭하면, ② 브라우저가 index.html을 읽고, 거기 연결된 style.css와 app.js까지 같이 읽어서, ③ 화면을 그립니다. 따로 켜야 할 프로그램이 없어요. 주소창을 보면 file로 시작하는데, 내 컴퓨터 안의 파일을 직접 열었다는 뜻입니다. 그래서 이 주소는 다른 사람에게 보내도 안 열려요. 파일을 고친 뒤 화면이 그대로면 새로고침, macOS는 ⌘R, Windows는 F5. 이것만 기억하시면 됩니다.

곁들일 이야기바탕화면의 문서 파일을 더블클릭해서 여는 것과 똑같습니다. 다만 그 문서를 여는 프로그램이 한글이나 워드가 아니라 브라우저인 거죠. 남에게 보여 주려면 공유 링크가 필요한데, 그게 1-7의 배포입니다.

118Node.js

그런데 실습하다 보면 「로그인 기능 넣어 줘」 같은 요청을 하게 되죠. 그러면 Claude Code가 index.html 세 파일이 아니라 Next.js라는 걸로 만들기 시작합니다. 그 바탕이 되는 Node.js부터 보겠습니다. 왼쪽이 브라우저예요. 크롬 안에는 V8이라는 JS 실행기가 들어 있습니다. 원래 JS는 이렇게 브라우저 안에서만 돌았어요. 2009년에 이 엔진을 브라우저 밖으로 꺼내서, 내 컴퓨터에서 바로 JS를 돌리게 만든 게 Node.js입니다. 오른쪽처럼 브라우저 밖으로 나오니까 할 수 있는 일이 늘었어요. 파일을 읽고 쓰고, 서버를 열고, 로그인할 때 비밀번호를 확인하는 일까지. 브라우저 안 JS는 누구나 코드를 열어 볼 수 있어서 비밀번호 확인 같은 건 맡길 수 없거든요. 그래서 로그인이 나오는 순간 Node.js가 필요해집니다.

곁들일 이야기V8은 자동차 엔진 이름이기도 하죠. 그 엔진을 차에서 떼어 다른 데 단 게 Node.js라고 보시면 됩니다.

119웹 구조 · Next.js

이제 Next.js인데, 그 전에 웹이 어떻게 돌아가는지부터 한 장으로 보겠습니다. 칸이 셋이에요. 왼쪽 클라이언트는 여러분 브라우저, 가운데 웹 서버는 요청을 받아 처리하는 프로그램, 오른쪽 DB는 데이터를 저장해 두는 곳입니다. 미니 노션에 로그인하는 장면 하나를 따라가 볼게요. ① 주소창에 localhost:3000/login을 치면 브라우저가 서버에 화면을 달라고 요청합니다. ② 서버가 HTML · CSS · JS를 보내 주면 로그인 화면이 뜨죠. ③ 이메일과 비밀번호를 넣고 로그인을 누르면 서버로 갑니다. ④ 서버는 DB에 이 이메일 쓰는 사람이 있는지 찾고, ⑤ DB가 저장된 정보와 페이지 목록을 돌려줍니다. ⑥ 서버가 비밀번호를 비교해서 맞으면, ⑦ 통과와 함께 내 페이지 목록을 보내 줘서 화면이 바뀝니다. 위에 괄호 보이시죠. Next.js는 이 중에 화면 코드와 서버 코드를 한 프로젝트에 같이 담는 도구입니다. React 기반이고, 1-7에서 배포할 Vercel이 만들었어요. page.tsx가 화면, api 폴더의 route.ts가 서버 쪽 로그인 처리, 그리고 그 서버를 실제로 돌리는 게 앞에서 본 Node.js입니다. 비밀번호 확인 코드는 서버에만 있어서 브라우저에선 안 보여요. DB는 괄호 밖이죠. 2부에서 Supabase로 붙입니다. 실행은 Claude Code에 「실행해 줘」 하면 localhost:3000이 열립니다. 화면 보는 법을 알았으니, 이제 개발 계획의 태스크를 하나씩 만들어 보겠습니다.

모드 정했으면 이제 만들어야죠. 그런데 개발계획.md의 태스크를 한 방에 다 시키면 어떻게 될까요? 문제가 세 가지 생깁니다. 첫째, 여러 파일이 한꺼번에 바뀌니까 오류가 어디서 났는지 찾기가 어렵습니다. 둘째, 연쇄 오류가 납니다. 「/」 메뉴를 고쳤더니 엔터로 새 블록 만드는 게 망가지는 식이에요. 둘 다 키보드 입력을 다루는 기능이라 한쪽을 건드리면 다른 쪽이 흔들리기 쉽거든요. 셋째, 중간 커밋이 없으니 돌아갈 곳이 없습니다. 하나씩 하면 요청은 태스크 수만큼 늘어요. 대신 문제가 생겨도 범위가 태스크 하나로 좁혀집니다. 1-4에서 굳이 기능 하나를 태스크 하나로 쪼개 둔 이유가 바로 이겁니다.

곁들일 이야기시험 문제 내기 전에 정답지부터 만들어 두는 거랑 같아요. 정답지 없이 채점하면 답안 하나 받을 때마다 「이게 맞나?」 하고 다시 따져야 하잖아요. Claude Code 공식 문서도 「Claude에게 통과 · 실패가 나오는 확인 방법을 주라」고 권합니다.

124태스크 진행 순서

태스크 하나는 이 순서로 돕니다. 맨 앞이 방금 본 테스트 케이스예요. 만들기 전에 「이걸 넣으면 이렇게 돼야 한다」, 입력과 기대 결과를 먼저 적습니다. 그다음 「이 태스크만, 이 케이스로 확인해 줘」 하고 요청하고, 브라우저에서 케이스대로 직접 눌러 봅니다. 다르게 나오면 기대 결과, 실제 결과, 오류 원문을 붙여서 고쳐 달라고 하고, 케이스가 전부 통과하면 그제서야 커밋합니다. 확인하고 고치는 건 통과할 때까지 몇 번을 돌아도 괜찮아요. 다만 그 태스크 문제는 그 태스크 안에서 끝내고 넘어가세요. 숙제를 다음 태스크로 들고 가면 안 됩니다.

곁들일 이야기저는 실제로 작업할 때 매번 테스트 케이스부터 만들고 시작합니다. 귀찮아 보여도 이게 제일 빨라요. Claude Code 공식 Best practices 문서도 「통과 · 실패가 나오는, Claude가 직접 돌려 볼 수 있는 것을 주라」고 합니다. 기대 결과가 먼저 있으면 「다 됐습니다」라는 말이 아니라 케이스 통과 여부로 끝을 판단할 수 있죠.

125태스크 요청 예시

요청 문장도 태스크 크기에 맞춥니다. 「나머지 다 만들어 줘」, 이러면 아까 그 한 방 구현으로 돌아가는 거예요. 대신 이렇게 말합니다. 「개발 계획에서 「/」 메뉴 태스크만 진행해 줘. 빈 블록에 「/」를 넣고 「체크 상자」를 고르면 그 블록이 체크 상자로 바뀌어야 해. 이 케이스로 확인해 줘.」 개발계획.md는 Claude Code가 직접 열어 읽으니까, 내용을 복사해 붙일 필요 없어요. 태스크 이름만 말하면 됩니다. 거기에 테스트 케이스, 입력과 기대 결과만 붙이면 Claude도 그 기준으로 만들고, 여러분은 그 결과가 나왔는지만 보시면 됩니다.

곁들일 이야기팀원한테 「보고서 마무리해 줘」라고 하면 서로 생각하는 「마무리」가 다르죠. 「3장 표만 채워 줘. 표에 지난달 숫자가 들어가 있으면 돼」라고 하면 확인이 1분이면 끝납니다. AI한테도 똑같아요.

126오류 해결 과정 비교

만들다 보면 오류는 당연히 납니다. 안 나면 오히려 수상해요. 과거에는 빨간 오류 메시지를 복사해서 구글이나 Stack Overflow에 검색하고, 비슷한 질문 찾아서 영어 답변 읽고, 내 코드에 맞게 직접 고쳤습니다. 고쳤는데 다른 오류가 나면? 처음부터 다시였죠. 바이브코딩에서는 증상이랑 오류 화면을 그대로 넘기면, AI가 파일을 읽고 원인을 찾아서 고칩니다. 여러분은 브라우저에서 다시 눌러 보고, 안 되면 달라진 점을 그대로 다시 말하면 돼요. 고치기 전에 원인부터 말해 달라고 하고, 두 번 고쳐도 안 되면 되돌리고 새 대화에서 다시 요청합니다. 이 순서는 단원 끝에서 한 장으로 정리해 드릴게요.

곁들일 이야기Karpathy가 처음 「vibe coding」을 말할 때 이렇게 썼어요. 오류 메시지가 나오면 아무 설명 없이 복사해 붙이고, 그래도 안 되면 증상이 사라질 때까지 이것저것 바꿔 달라고 한다고요. 주말 장난감 프로젝트라면 그래도 됩니다. 남이 쓸 앱이라면, 테스트 케이스랑 기대 결과를 같이 주는 쪽이 훨씬 빨리 끝나요.

127버그 알리는 방법

버그를 찾았으면 AI한테 알려야겠죠. 위에 줄 그은 것처럼 「「/」 메뉴가 안 돼요」 한 줄만 보내면, AI는 어디서 뭘 했는지 모르니까 짐작으로 아무 데나 고칩니다. 왼쪽이 실제 상황이에요. 빈 블록에 「/」를 쳤는데 메뉴가 안 열립니다. 이때 F12, 맥은 옵션 커맨드 J를 누르면 아래에 검은 Console 창이 뜨고, 빨간 줄이 보여요. 이게 오류 원문입니다. 읽을 줄 몰라도 됩니다. 그대로 복사만 하세요. 오른쪽이 실제로 입력창에 쓰는 모양입니다. 첫 줄에 증상, 그리고 ① 어떤 순서로 눌렀는지, ② 원래 어떻게 되어야 하는지, ③ 실제로는 어땠는지, ④ 빨간 줄 복사한 것, ⑤ 화면 캡처. 이렇게 보내면 AI가 app.js 87번째 줄부터 바로 봅니다. 기대 결과는 앞에서 만든 테스트 케이스를 그대로 옮기면 돼요.

곁들일 이야기전산팀에 전화해서 「컴퓨터가 이상해요」라고 하면, 전산팀도 같이 이상해집니다. 「엑셀에서 저장 버튼 누르면 이런 창이 뜨고 꺼져요」라고 하면 금방 해결되죠. 오류가 매번 생기는지, 가끔 생기는지도 같이 알려 주면 더 좋습니다.

128구체적 수정 요청

증상을 전할 때 말하는 방식에 따라 결과가 확 달라집니다. 「더 예쁘게 해 줘」, 이러면 뭘 바꿀지를 AI가 마음대로 정해요. 대신 「왼쪽 목록에서 긴 페이지 제목이 잘려. 목록 폭은 그대로, 제목은 두 줄까지 보이게」처럼 말합니다. 어디가, 지금 어떤 상태고, 원하는 결과가 뭔지. 이 세 칸을 채우고, 한 번에 하나씩만 요청하세요. 여기서 원하는 결과가 곧 그 수정의 테스트 케이스가 됩니다.

곁들일 이야기미용실에서 「알아서 예쁘게요」 하면 결과는 미용사님 취향입니다. 가끔 대단히 과감한 취향을 만나기도 하죠. 「앞머리는 눈썹 위까지, 옆은 그대로」라고 하면 원하는 모양에 훨씬 가깝게 나옵니다.

129화면 캡처 첨부

말로 설명하기 어려운 화면 문제는 캡처 붙이는 게 제일 빠릅니다. 입력창에 붙여 넣거나 파일을 끌어다 놓으면 돼요. 붙인 다음엔 「캡처에서 오른쪽 위 버튼」처럼 어디를 보면 되는지 짚어 주고, 브라우저에 오류 문구가 떴다면 그 문구도 그대로 복사해 붙입니다. 예시를 보면, 「「/」 메뉴가 화면 아래로 잘려서 「구분선」이 안 보여. 메뉴가 화면 안에 다 보이게 해 줘」라고 했더니, Claude가 아래 공간이 모자랄 땐 메뉴를 블록 위쪽에 열리게 바꿨다면서 새로고침해서 확인해 달라고 답합니다. 그 말만 믿지 마시고요, 페이지 맨 아래 블록에서 「/」를 직접 다시 쳐 보세요.

곁들일 이야기캡처 단축키는 맥은 Command+Shift+4, 윈도우는 Windows 키+Shift+S입니다. 회사 IT 지원팀에 문의하면 첫 답장이 늘 「화면 캡처 첨부해 주세요」잖아요. 같은 이유입니다.

130Git으로 되돌리기

고쳐 달라고 했는데 오히려 전보다 나빠질 때도 있습니다. 네, 생각보다 자주 있어요. 이럴 때 1-5에서 배운 커밋이 빛을 봅니다. 「마지막 커밋 상태로 되돌려 줘」라고 하면, 예시처럼 마지막 커밋 이후에 고친 style.css를 되돌려요. 그다음 어디 · 지금 · 원하는 것, 세 칸 형식으로 다시 요청하면 됩니다. 테스트 케이스를 통과한 다음에만 커밋했으니, 돌아간 곳은 적어도 케이스가 통과하던 상태예요. 태스크마다 남긴 커밋이 게임의 세이브 포인트가 되는 겁니다.

곁들일 이야기구글 문서 「버전 기록」 써 보신 분은 익숙하실 거예요. 문서가 엉망이 돼도 어제 버전으로 돌아갈 수 있으니까 마음 놓고 고치게 되죠. 커밋이 있으면 코드도 그렇게 대담하게 고칠 수 있습니다.

131체크포인트와 Git

Claude Code에는 커밋이랑 비슷해 보이는 체크포인트라는 기능도 있어요. 요청할 때마다 자동으로 남고, /rewind나 Esc 두 번으로 코드나 대화, 또는 둘 다를 되감을 수 있습니다. 편하죠. 다만 Bash 명령으로 바뀐 파일이나 Claude Code 밖에서 직접 고친 파일은 못 잡아요. Git 커밋은 내가 「커밋해 줘」 한 시점에 남고, 지우기 전까지 계속 남고, GitHub에도 올라갑니다. 공식 문서도 체크포인트가 버전 관리를 대신하지 않는다고 적어 두었고, 다음 단원 1-7 배포도 커밋을 씁니다.

곁들일 이야기엑셀의 Ctrl+Z랑 「다른 이름으로 저장」 차이랑 비슷합니다. Ctrl+Z는 편하지만 그 작업 안에서만 통하고, 따로 저장한 파일은 나중에도 꺼내 볼 수 있죠. 체크포인트는 Ctrl+Z, 커밋은 저장한 파일 쪽입니다.

132바이브 디버깅 순서

문제가 생겼을 때의 순서로 묶어 보겠습니다. 테스트 케이스와 다르게 나오면 재현 방법, 기대 결과, 실제 결과, 오류 원문을 전달하고요. 그리고 바로 고치라고 하지 말고, 「고치기 전에 원인부터 말해 줘」. 원인을 듣고 고친 다음 테스트가 통과하면, 1-5에서 배운 커밋으로 그 상태를 저장합니다. 마지막 하나가 중요해요. 같은 문제를 두 번 고쳐 달라고 했는데도 안 되면, 세 번째로 매달리지 마세요. 저장해 둔 시점으로 되돌리고, 새 대화에서 더 나은 요청으로 다시 시작합니다. 이게 Claude Code 공식 문서가 권하는 방식이기도 합니다.

곁들일 이야기AI가 「다 됐습니다」 해도, 실행 결과나 화면을 직접 확인하는 습관이 제일 중요합니다. Simon Willison은 「실행되는 걸 직접 보지 않았다면 동작하는 시스템이 아니다」라고 썼고, Kent Beck은 AI가 테스트를 지우거나 꺼서 통과한 것처럼 만드는 경우를 경고 신호로 꼽았죠. 그러니까 「테스트 통과했습니다」라는 말이 나오면, 테스트가 그대로 살아 있는지도 한 번 들여다보세요.

133실습 1-6

자, 이제 직접 해 보실 차례입니다. 목표는 여러분 개발계획.md에 있는 태스크를 하나씩 만들고, 완료 기준을 전부 확인하는 거예요. 쓰는 파일은 1-4에서 만든 개발계획.md, 그리고 1-5에서 만든 Git 폴더입니다. 계획은 이미 있으니까 바로 첫 태스크 요청부터 들어가세요. 단, 요청하기 전에 그 태스크의 테스트 케이스 한 줄은 먼저 적어 두시고요. 브라우저로 확인하고 커밋, 다음 태스크도 같은 순서로 반복, 마지막에 완료 기준 대조. 다 끝났을 때 완료 기준이 전부 체크돼 있고, 커밋 기록에 커밋이 여러 개 쌓여 있으면 성공입니다.

곁들일 이야기미니 노션 말고 「회의실 예약표」나 「간식 주문 취합」으로 계획 세우신 분도 걱정 마세요. 기능 이름이랑 테스트 케이스만 다를 뿐, 순서는 똑같습니다.

134실습 1-6 순서

다섯 단계입니다. 「개발계획.md의 첫 태스크만 만들어 줘」처럼 태스크 하나를 요청하고, 브라우저로 직접 눌러 보고, 그 기능의 완료 기준이랑 맞춰 본 다음 「커밋해 줘」, 그리고 다음 태스크. 태스크를 다 만들면 마지막으로 Claude에게 순서도를 그리게 하고, 빠진 조건을 피드백합니다. 처음 몇 태스크는 Manual 모드로 두고 수정마다 확인하세요. 막히기 쉬운 곳은 두 군데입니다. 고쳤는데 화면이 그대로면 새로고침부터. 그리고 커밋 깜빡하고 다음 태스크로 넘어가지 않기. Claude가 엉뚱한 쪽으로 만들기 시작하면 Esc로 멈추고 다시 요청하세요. 이미 망가졌다면 「마지막 커밋으로 되돌려 줘」로 돌아가면 됩니다.

곁들일 이야기내비게이션이 엉뚱한 길로 안내하면 끝까지 따라가지 않잖아요. 중간에 경로를 다시 잡죠. Esc가 그 버튼입니다. Claude Code 공식 문서도 처음 1분쯤 지켜보다가 방향이 틀리면 Esc로 멈추라고 권해요.

135실습 1-6 · 1단계 태스크 하나 요청

드디어 앱을 만듭니다. 「개발계획.md의 첫 태스크만 만들어 줘」. 태스크 번호와 이름은 사람마다 다르게 나오니 옆자리와 달라도 괜찮습니다. 딱 하나만요. 파일을 만들 때마다 패널에서 승인을 묻는데, 내용을 훑어보고 승인. 이 대화 동안 자동 승인을 고르면 다음부터는 묻지 않습니다. 익숙해지면 그쪽이 편해요.

136실습 1-6 · 2단계 브라우저 확인

만들어졌으면 브라우저로 직접 확인합니다. 방금 만든 기능을 테스트 케이스대로 눌러 보세요. 파일을 고친 뒤에는 새로고침부터. 기대한 것과 다르면 기대 결과, 실제 결과, 오류 원문을 붙여서 고쳐 달라고 합니다. 화면은 사람마다 다르게 나옵니다. 저도 지금 하나 만들어 보면서 같이 보겠습니다.

137실습 1-6 · 3단계 완료 기준 대조

146문서 파일과 공유 링크

더 익숙한 장면으로 바꿔 볼게요. 바탕화면에 있는 문서 파일은 내 컴퓨터에서만 열리죠. 이게 localhost입니다. 같은 문서를 온라인 문서 서비스에 올려서 공유 링크를 만들면, 팀장님도 팀원도 휴대폰으로도 열 수 있습니다. 이 공유 링크가 배포 주소, *.vercel.app에 해당해요. 그리고 문서를 고치면 링크로 보는 사람한테 바로 반영되죠. 배포에서는 이걸 재배포라고 부릅니다. 뒤에서 보겠지만 push만 하면 자동으로 됩니다.

곁들일 이야기메일에 파일 첨부해서 돌리다 보면 「최종_진짜최종_v3.docx」 같은 파일이 여기저기 굴러다니죠. 다들 한 번씩 만들어 보셨을 겁니다. 공유 링크는 주소가 하나라서 모두가 항상 최신본을 봅니다. 배포 주소도 똑같아요. 고칠 때마다 새 파일을 돌리는 게 아니라 같은 주소의 내용이 바뀝니다.

147localhost · 내부망 · 외부망

그럼 정말로 내 컴퓨터의 앱은 다른 기기에서 못 여는 걸까요? 화면을 보시면 상자가 세 겹입니다. 맨 안쪽이 내 컴퓨터, 내 브라우저에서는 localhost:8000이 열립니다. 그 바깥이 공유기 안, 같은 Wi-Fi에 붙은 내부망이에요. 여기서는 내 컴퓨터의 내부 주소 192.168.0.12:8000으로 팀원 노트북이나 내 휴대폰에서도 열립니다. 생각보다 되죠? 그런데 집에 있는 사람이나 LTE로 접속한 휴대폰은 같은 주소를 쳐도 안 열립니다. 192.168로 시작하는 주소는 공유기 안에서만 통하는 주소거든요. 그래서 인터넷 어디서나 열리는 Vercel 서버에 올려 두고, mini-notion.vercel.app으로 열게 하는 겁니다.

곁들일 이야기집 공유기 설정 들어갈 때 주소창에 192.168.0.1이나 192.168.1.1 쳐 보신 분 계실 거예요. 그 주소도 집 와이파이에 붙어 있을 때만 열립니다. 회사 프린터가 회사 Wi-Fi에서는 되는데 집에서는 안 되는 것도 같은 원리예요. 집에서 회사 프린터로 출력 눌러 본 분, 계시죠.

148주소별 접속 범위

방금 본 주소 세 개를 표로 정리했습니다. 1-6에서 더블클릭으로 연 file 주소나 localhost는 이 컴퓨터만 열 수 있습니다. 192.168.0.12:8000 같은 내부 주소는 내 컴퓨터에 서버를 띄웠을 때 같은 Wi-Fi나 회사망 기기에서 열리니까, 배포 전에 내 휴대폰으로 화면 볼 때 쓸 수 있습니다. mini-notion.vercel.app은 인터넷의 누구나 열 수 있고, 남한테 공유할 때 씁니다. 참고로 192.168 같은 사설 주소 규칙은 RFC 1918이라는 인터넷 표준 문서에 정해져 있어요. 외울 필요는 없습니다.

곁들일 이야기localhost는 사실 127.0.0.1이라는 숫자 주소를 가리키는 이름입니다. 어느 컴퓨터에서든 「나 자신」을 뜻하는 주소라서, 개발자들은 「127.0.0.1만 한 곳은 없다(There's no place like 127.0.0.1)」라는 농담까지 만들었어요. 집만 한 곳이 없다는 말을 이렇게 바꿔 놓은 겁니다.

149배포 흐름

그럼 배포가 실제로 어떤 길을 거치는지 보겠습니다. 내 컴퓨터에 앱과 커밋이 있고, 이걸 GitHub에 올립니다. 1-5에서 배운 코드 보관소죠. Vercel은 GitHub에 있는 코드를 가져가서 인터넷에 공개하고, *.vercel.app 주소를 줍니다. 다른 사람은 그 링크로 들어오고요. 우리가 할 연결은 딱 두 개입니다. 첫째, GitHub에 빈 저장소를 하나 만들고 Claude Code가 거기에 올리게 하는 것. 둘째, GitHub와 Vercel을 한 번 이어 두는 것. 한 번 이어 두면 그다음부터는 알아서 굴러갑니다.

곁들일 이야기블로그 글 하나를 여러 SNS에 자동으로 퍼 나르게 설정해 두는 것과 비슷합니다. 원본은 한 곳, GitHub에만 올리고, 공개하는 일은 연결된 서비스 Vercel이 알아서 합니다.

곁들일 이야기2022년 도요타가, 자사 서비스 소스 코드 일부가 외부 협력사 실수로 공개 저장소에 수년간 올라가 있었고 그 안에 데이터 서버 접근 키가 들어 있었다고 발표한 일이 있습니다. 그 큰 회사에서도 키가 코드에 섞여 공개되는 일이 생깁니다. 우리라고 예외일 리 없죠. 그래서 올리기 전에 한 번 찾아보는 단계를 습관으로 넣습니다.

153GitHub 업로드 요청

저장소가 생겼으면 이제 말로 시킵니다. 「이 폴더를 GitHub 저장소 https://github.com/내계정/mini-notion 에 올려 줘」. 방금 복사한 주소를 붙여 넣으면 돼요. 그러면 Claude가 git remote add로 시작하는 명령, 이 주소를 내 폴더에 등록하는 명령과, git push로 지금까지의 커밋을 올리는 명령을 보여 주면서 실행해도 되냐고 묻습니다. 「응」 하고 허락하면 1-5부터 쌓은 커밋이 그대로 GitHub에 올라갑니다. 명령은 몰라도 돼요. 다만 Claude가 허락을 구할 때 주소가 내가 만든 저장소가 맞는지 정도는 눈으로 확인하는 습관을 들이세요.

곁들일 이야기은행 앱에서 이체 누르면 「받는 분 · 금액이 맞습니까」 하고 한 번 더 묻죠. 화면 내용을 다 이해 못 해도 받는 사람 이름 정도는 보고 누르잖아요. Claude가 명령 실행 전에 묻는 것도 같은 확인 단계입니다. 습관처럼 「응」만 누르면 은행 앱에서 그러는 것만큼 위험합니다.

154업로드한 저장소 확인

올라갔으면 Claude가 알려 준 주소를 브라우저로 열어 봅니다. 볼 곳은 세 군데예요. 하나, 파일 목록이 내 폴더랑 같은지. index.html, style.css, app.js에 1-3의 기획서.md, 1-4의 개발계획.md까지 다 있어야 합니다. 둘, 커밋 기록에 1-5와 1-6에서 한 커밋들이 남아 있는지. 셋, 저장소 이름 옆에 Public 표시가 있는지.

곁들일 이야기택배 보내고 송장 번호로 배송 조회 한 번 해 보는 거랑 같습니다. Claude가 「완료」라고 했어도, 직접 열어 보는 게 진짜 확인이에요.

155Vercel 프로젝트 가져오기

자, 이제 두 번째 연결, GitHub에서 Vercel로 넘어갑니다. 1-2에서 만든 GitHub 계정으로 Vercel에 로그인하고, 새 프로젝트에서 Git 저장소 가져오기를 고릅니다. 목록에서 mini-notion을 선택하고 Deploy를 누르면 끝이에요. 설정은 기본값 그대로 둡니다. 우리 앱은 HTML · CSS · JS 파일만 있는 폴더라서 빌드 설정을 건드릴 게 없거든요. 보통 1분 안팎이면 주소가 나옵니다. 제일 자주 막히는 곳은 목록에 내 저장소가 안 보이는 경우예요. 그럴 땐 GitHub 쪽에서 Vercel이 그 저장소에 접근하도록 허용해 줘야 합니다. 화면에 나오는 권한 설정 링크를 따라가서 저장소를 추가하세요.

곁들일 이야기새로 깐 사진 편집 앱이 「사진 접근 허용」을 물을 때 「선택한 사진만」을 고르면, 나머지 사진은 앱에서 안 보이죠. Vercel도 똑같이 GitHub에서 허용받은 저장소만 볼 수 있습니다.

156배포 주소

배포가 끝나면 주소가 두 종류 보입니다. 하나는 프로젝트 기본 주소, 프로젝트명.vercel.app 형식이에요. 우리 예제라면 mini-notion.vercel.app이죠. 다른 하나는 배포할 때마다 새로 생기는 고유 주소로, mini-notion-a1b2c3처럼 뒤에 글자가 붙습니다. 버전마다 따로 생기고 기본적으로 공개예요. 그럼 남한테는 뭘 보내느냐. 기본 주소입니다. 다시 배포해도 안 바뀌니까요.

곁들일 이야기온라인 문서의 버전 기록을 떠올리시면 됩니다. 문서 링크는 하나지만, 버전 기록을 열면 과거 시점 모습을 따로 볼 수 있죠. 기본 주소는 항상 최신본, 배포마다 생기는 주소는 그 시점의 사본입니다.

157배포 화면

이게 배포 주소로 연 미니 노션을 390px 휴대폰 폭에서 본 화면입니다. 내 컴퓨터에서 보던 거랑 코드는 똑같고 주소만 다릅니다. 개발 계획 완료 기준 마지막 줄 기억나세요? 「모바일 폭(390px)에서도 가로 스크롤 없이 보인다」. 배포했으니 이제 진짜 휴대폰으로 확인할 수 있어요. 주소를 메신저로 나한테 보내서 휴대폰으로 열어 보세요. 왼쪽 페이지 목록이 화면을 가리거나 글이 옆으로 삐져나가면, 1-6에서 했던 대로 화면 캡처해서 붙이고 고쳐 달라고 하면 됩니다.

곁들일 이야기카카오톡 「나와의 채팅」에 주소를 보내 두면 휴대폰에서 바로 눌러 열 수 있습니다. 긴 주소를 손으로 옮겨 치다가 한 글자 틀려서 「사이트에 연결할 수 없음」 보는 일을 막아 줍니다.

158수정 → 재배포

배포는 한 번으로 끝나지 않습니다. 앱은 계속 고치게 되거든요. 여기서 아까 연결해 둔 효과가 나옵니다. 화면 예처럼 「체크한 할 일 글자를 연한 초록으로」 같은 수정을 요청하고, 내 컴퓨터에서 새로고침으로 확인한 다음, 「커밋하고 GitHub에 올려 줘」라고 말합니다. 그러면 push가 되고, Vercel이 그 push를 알아채서 1~2분 안에 새로 배포합니다. 결과는 같은 주소에 반영돼요. 이미 주소를 받은 사람한테 새 링크를 다시 보낼 필요가 없습니다. 정리하면 수정 요청, 내 컴퓨터에서 확인, 커밋과 push, 자동 배포, 같은 주소 반영. 다섯 단계입니다.

곁들일 이야기식당 테이블에 QR 메뉴판 붙여 둔 가게는 메뉴가 바뀌어도 QR 스티커를 새로 뽑지 않습니다. QR이 가리키는 페이지 내용만 바꾸면 되죠. 배포 주소가 그 QR이고, push가 메뉴 페이지를 고치는 일입니다.

159실습 1-7

이제 직접 해 볼 차례입니다. 목표는 1-6에서 만든 내 앱을 GitHub에 올리고 Vercel 주소로 공개하는 것. 쓰는 폴더는 1-6의 내 앱 폴더입니다. GitHub 로그인은 1-5에서 해 뒀으니, 순서는 올리기 전 점검, GitHub에서 공개 저장소 만들기, Claude Code에 업로드 요청, Vercel에서 가져오기와 Deploy, 그리고 휴대폰으로 열어 보기. 마지막으로 한 곳을 고쳐서 push하고, 같은 주소에 반영되는지까지 봅니다. 완료 기준은 세 가지예요. 저장소에 내 파일과 커밋 기록이 있고, *.vercel.app 주소로 앱이 열리고, 수정 한 번이 재배포로 반영되면 끝입니다.

160실습 1-7 순서

순서를 다섯 단계로 다시 짚겠습니다. GitHub 로그인은 1-5에서 해 뒀습니다. 혹시 안 됐으면 「로그인됐는지 확인해 줘」부터. 1번, 올리기 전에 키와 개인정보 점검 요청. 2번, github.com에서 공개 저장소 만들기. 3번, 올려 달라고 요청. 4번, Vercel에서 가져오기와 Deploy. 5번, 한 곳 고쳐서 커밋 · push 요청. 자주 막히는 곳은 한 군데입니다. 곁들일 이야기앱 스토어 앱 소개도 첫 줄에 「무엇을 하는 앱인지」를 한 문장으로 쓰고, 나머지는 스크린샷으로 보여 주죠. 공유 글의 한 줄 소개도 그 첫 문장이라고 생각하고 쓰시면 됩니다.

보여 줬으면 이제 스스로 돌아볼 차례입니다. 질문은 네 개예요. 요청과 결과가 달랐던 곳은 어디였고, 첫 요청에 어떤 말이 빠져 있었나. 기획서랑 비교해서 만들다가 빼거나 더한 기능은 뭔가. 커밋으로 되돌린 순간이 있었나. 그리고 써 보니 아쉬워서 다음에 붙이고 싶은 기능은 뭔가. 답은 개발계획.md 맨 아래에 「회고」 칸을 만들어서 적습니다. 머릿속에만 두면 내일이면 잊어버려요. 이 기록이 2부 기획의 출발점이 됩니다.

곁들일 이야기회사에서 프로젝트 회고할 때 자주 쓰는 방식으로 KPT가 있습니다. 계속할 것(Keep), 문제였던 것(Problem), 다음에 해 볼 것(Try)으로 나눠 적는 방식이에요. 오늘 질문 네 개도 결국 이 세 칸 중 하나에 들어갑니다.

170데이터 저장 위치 · localStorage

회고하다 보면 이런 걸 발견한 분이 계실 거예요. 같은 배포 주소를 팀원 휴대폰으로 열었더니, 내가 써 둔 「주간 회의록」은 없고 「시작하기」 한 장만 덩그러니 나옵니다. 「어, 날아갔나?」 싶으시죠. 고장 아닙니다. 현재 앱은 페이지를 localStorage, 그러니까 각자의 브라우저 안에 저장하거든요. 내 노트북 브라우저에는 주간 회의록과 아이디어 메모가 있고, 팀원 휴대폰 브라우저는 처음 열었으니 처음 화면 그대로인 겁니다. 내 회의록을 다른 사람이랑 같이 보려면, 모두가 같은 곳에 쓰고 같은 곳에서 읽는 저장소가 필요해요. 그게 데이터베이스고, 2-2와 2-5에서 다룹니다.

곁들일 이야기엑셀 파일을 각자 PC에 복사해 두고 적는 것과, 온라인 공유 시트 하나에 다 같이 적는 것의 차이입니다. 현재 앱은 각자 자기 PC 엑셀에 적고 있는 상태예요. 앱 모양은 똑같아도 적힌 내용은 다 다릅니다. 같은 이유로 회사 PC에서 쓴 메모가 집 노트북에서는 안 보입니다.

1711부의 한계와 2부

localStorage 말고도 현재 앱에 없는 게 몇 가지 있습니다. 페이지를 공유할 수 없고 브라우저마다 따로 저장되는 문제는 Supabase 데이터베이스로, 2-2와 2-5에서 풉니다. 앱이 다른 서비스랑 따로 놀아서 날짜나 캘린더 정보를 사람이 직접 확인해야 하는 문제는 외부 API와 MCP로, 2-3과 2-6에서 다룹니다. 기능마다 직접 눌러 보며 오류를 찾는 수고는 테스트와 디버깅으로, 2-7에서 덜어 냅니다. 앱이 잘 돌아가는지 사용자 제보로만 알 수 있는 문제는 모니터링과 로그로, 2-8에서 다룹니다. 나머지도 2부에서 하나씩 더합니다. 2부 공통 예제는 미니 노션이 아니라 「팀 할 일 보드」입니다. 처음부터 여럿이 같이 쓰는 앱이라서, 기획서부터 개발 계획, 개발까지 같은 순서를 한 번 더 밟습니다.

곁들일 이야기예를 들어 미니 노션에 회의록을 쓸 때, 회의 날짜는 캘린더 앱을 따로 열어 보고 손으로 옮겨 적고 계실 겁니다. 앱이 캘린더랑 이어져 있으면 그 단계가 없어지죠. 이렇게 다른 서비스와 이어 붙이는 방법이 2부의 API와 MCP입니다.

1722부 커리큘럼

2부 지도입니다. 2-1에서 데이터베이스와 MCP를 미리 보고, 2-2에서 표 · 행 · 열과 Supabase, 2-3에서 API와 MCP를 배웁니다. 2-4에서는 1부처럼 다시 기획부터 하는데, 이번엔 개발 계획에 데이터 · 연동 · 권한이 들어갑니다. 2-5에서 저장 · 조회 · 로그인, 2-6에서 API 키와 MCP로 외부 서비스 연결, 2-7에서 테스트와 디버깅, 2-8에서 환경변수와 로그를 다루며 배포와 모니터링을 하고, 2-9에서 운영 체크리스트로 마무리합니다. 길어 보이지만 뼈대는 익숙해요. 1부의 기획, 개발 계획, 개발, 배포 흐름이 한 번 더 도는 구조입니다.

곁들일 이야기운전면허 따고 동네 길 몇 번 다닌 다음에 고속도로에 나가는 것과 비슷합니다. 운전하는 방법은 같아요. 속도와 챙길 것이 늘어날 뿐입니다.

173회고 기록

마지막으로 이 표를 채웁니다. 배포 주소, 완료 기준 몇 개 중 몇 개 통과, 요청과 결과가 달랐던 곳, 기획서와 달라진 것, 2부에서 붙이고 싶은 것. 앞에서 말로 나눈 걸 글로 남기는 단계예요. 이 표랑 기획서.md, 개발계획.md, 이 세 가지를 2부로 가져갑니다. 2-4에서 다시 기획할 때 이 세 문서가 출발점이 돼요. 특히 「2부에서 붙이고 싶은 것」 칸은 비워 두지 마시고, 하나라도 꼭 적어 주세요.

곁들일 이야기예를 들어 「회의록 페이지를 팀원도 같이 봤으면」 한 줄만 적어 둬도, 그게 그대로 2부 데이터베이스 단원에서 내가 풀 문제가 됩니다. 막연한 「더 좋게」보다, 쓰다가 불편했던 장면 하나가 다음 기획에 훨씬 쓸모 있어요.

1741-8 산출물

1부의 마지막 산출물은 회고 기록이고, 이게 그대로 2부로 가는 입력입니다. 2부 바이브 코딩 심화에서는 데이터베이스, 외부 연동, 품질 관리를 다룹니다. 예제는 여럿이 같이 쓰는 팀 할 일 보드로 바뀌지만, 기획서에서 시작해서 개발 계획, 개발로 가는 순서는 1부랑 똑같습니다. 1-1에서 코드 한 줄 안 써 봤다던 분들이 이제 손에 인터넷 주소 하나씩 들고 계십니다. 1부 수고 많으셨습니다.
