## 135 · 파일 이름 버전 관리
먼저 다들 겪어 본 장면부터요. 발표자료 하나 고치다 보면 _v2, _최종, _최종_수정, _진짜최종, _진짜진짜마지막까지 사본이 늘어납니다. 보면서 웃으시는 분들, 다 압니다. 그 폴더 있으시죠. 이렇게 관리하면 세 가지가 어렵습니다. 어느 게 최신인지 날짜나 내용을 열어 봐야 알고, 뭐가 바뀌었는지는 두 파일을 나란히 놓고 눈으로 비교해야 하고, 중간 사본을 지웠으면 그 상태로는 다시 못 돌아갑니다. Git이 바로 이 문제를 푸는 도구입니다.

> 곁들일 이야기 — 팀장님이 「사흘 전 버전에 있던 표 다시 살려 주세요」 하시면, 사본 여섯 개를 하나씩 열어서 표 있는 파일을 찾아야 합니다. 구글 문서나 워드의 「버전 기록」 기능이 이 수고를 줄이려고 나온 거고, Git은 같은 일을 폴더 전체 단위로 해 줍니다.

## 136 · 세이브 포인트
Git을 이해하는 제일 쉬운 방법은 게임의 세이브 포인트입니다. 보스 방 앞에서 저장해 두면, 져도 그 지점부터 다시 시작하죠. 처음부터 다시 하라고 하면 게임기 던지고 싶어집니다. Git에서 저장하는 일을 커밋, 저장 슬롯에 붙이는 이름을 커밋 메시지라고 합니다. 저장 목록은 기록, log고요, 저장 시점을 불러오는 게 되돌리기입니다. 그리고 게임 클라우드 저장처럼 기록을 인터넷에 올려 두는 곳이 GitHub입니다.

> 곁들일 이야기 — 게임기를 바꿔도 클라우드 저장 덕분에 이어서 할 수 있잖아요. GitHub에 올려 둔 기록도 마찬가지로, 노트북이 고장 나도 다른 컴퓨터에서 그대로 받아서 이어 작업할 수 있습니다.

## 137 · Git
비유를 실제 모습으로 바꿔 보겠습니다. 복사본으로 관리하면 파일마다 사본이 생기고, 바뀐 곳은 사람이 눈으로 찾아야 해요. Git으로 관리하면 파일은 기획서.md 하나 그대로입니다. 사본이 안 늘어나요. 대신 커밋할 때마다 뭐가 바뀌었는지가 자동으로 기록됩니다. git 공식 문서에서도 커밋을 「저장소에 변경을 기록하는 일」이라고 설명합니다.

> 곁들일 이야기 — Git은 2005년에 리누스 토르발스가 리눅스 커널 개발하려고 만든 도구입니다. 전 세계 개발자 수천 명이 같은 코드를 고치는 상황을 관리하려고 만든 건데, 현재는 혼자 일하는 사람도 똑같이 씁니다. 우리도 오늘부터 그 대열에 합류하는 겁니다.

## 138 · 커밋 구성
커밋 하나에는 네 가지가 들어 있습니다. 어느 파일 어느 줄이 바뀌었는지, 「버튼 추가」 같은 메시지, 언제 누가 했는지, 그리고 8fcbe80 같은 고유 번호. 이 번호를 해시라고 부르는데, 커밋마다 다르게 붙는 주민등록번호 정도로 생각하시면 됩니다. 이 중에서 사람이 신경 쓸 건 메시지 하나예요. 나중에 돌아갈 시점을 찾을 때 보는 이름표거든요.

> 곁들일 이야기 — 메시지를 전부 「수정」이라고만 남기면 어떻게 될까요. 기록이 스무 개 쌓였을 때 「수정, 수정, 수정…」 중에 어디로 돌아갈지 알 수가 없습니다. 파일 이름 「진짜최종」이랑 다를 게 없죠. 「로그인 버튼 추가」처럼 뭘 바꿨는지 한 줄이면 충분합니다.

## 139 · 커밋 기록 쌓기
커밋은 이렇게 아래에서 위로 쌓입니다. 첫 화면 완성, 버튼 추가, 색상 수정, 이 순서로 세 번 저장했어요. 오른쪽은 같은 기록을 터미널에서 git log --oneline으로 본 모습인데, 최신 커밋이 맨 위에 나옵니다. 앞에 붙은 문자 일곱 개가 방금 말씀드린 고유 번호예요.

> 곁들일 이야기 — 카톡 대화방을 위로 쭉 올려 보면 언제 무슨 말이 오갔는지 다 남아 있죠. 비슷합니다. 다만 Git 기록은 「뭘 바꿨는지」만 모아 둔 대화방이에요. 잡담은 없습니다.

## 140 · 되돌리기 방법
되돌리는 방법은 언제 되돌리느냐에 따라 둘로 나뉩니다. 아직 커밋 전이면 restore, 파일을 마지막 커밋 상태로 돌립니다. 방금 고친 게 마음에 안 들 때 씁니다. 이미 커밋한 뒤라면 revert를 씁니다. revert는 기록을 지우지 않아요. 대신 그 커밋을 거꾸로 되돌리는 새 커밋을 하나 더 만듭니다. 아래 화면 보시면 「Revert "색상 수정"」 커밋이 맨 위에 새로 생겼고, 원래 색상 수정 기록도 그대로 남아 있죠.

> 곁들일 이야기 — 카드 결제 취소해 보시면, 원래 결제 내역이 사라지는 게 아니라 「취소」 내역이 한 줄 더 찍힙니다. 회계에서도 틀린 전표를 지우지 않고 반대 전표를 새로 넣어서 바로잡죠. 그래야 나중에 무슨 일이 있었는지 따라갈 수 있습니다. 월말 정산 해 보신 분들은 이게 얼마나 고마운 건지 아실 거예요.

## 141 · Git 작업 요청
여기까지 명령어 이름이 꽤 나왔는데, 외우실 필요 없습니다. 시험 안 봐요. 바이브코딩에서는 Claude Code한테 말로 시킵니다. 「지금 상태 커밋해 줘」 하면 git add랑 git commit이 실행되고 메시지도 Claude가 씁니다. 「커밋 기록 보여 줘」는 git log, 「방금 고친 거 취소해 줘」는 git restore, 「마지막 커밋 되돌려 줘」는 git revert. 명령 실행은 Claude Code가 하고, 사람은 결과가 맞는지만 확인합니다.

> 곁들일 이야기 — 엑셀 함수 이름을 몰라도 「합계 내 줘」 하면 되는 것과 비슷합니다. 다만 이름을 한 번 들어 둔 덕분에, Claude가 「git revert를 실행했습니다」라고 답할 때 무슨 일이 일어났는지 알아들을 수 있죠. 그 정도면 충분합니다.

## 142 · GitHub
이제 GitHub입니다. Git은 내 컴퓨터 안에서 저장 시점을 기록하고 되돌리는 도구예요. 그러니까 Git만 쓰면 기록이 이 컴퓨터에만 있습니다. 노트북에 커피 쏟으면 기록도 같이 날아가는 거죠. GitHub는 그 기록을 인터넷에 보관하는 원격 저장소입니다. 내 컴퓨터 밖에 같은 기록을 하나 더 두는 거고, 다른 사람이랑 공유하거나 다른 컴퓨터에서 받을 수도 있어요. Free 요금제로도 비공개 저장소를 개수 제한 없이 만들 수 있고, 1-7에서는 이 GitHub 저장소를 Vercel 배포와 연결합니다.

> 곁들일 이야기 — Git이랑 GitHub, 이름이 비슷해서 같은 걸로 많이들 헷갈립니다. Git은 프로그램 이름이고, GitHub는 그 기록을 맡아 주는 서비스 이름이에요. 휴대폰 사진 앱이랑 사진 클라우드 관계쯤 됩니다. 참고로 GitHub는 2018년에 마이크로소프트가 인수했습니다.

## 143 · Git 작업 흐름
실제로 기록이 어떻게 움직이는지 애니메이션으로 보겠습니다. 작업 폴더에서 파일을 고치면, git add로 커밋할 파일을 스테이징 영역에 담습니다. 그다음 git commit으로 로컬 저장소에 기록을 남기고, git push로 그 기록을 GitHub에 올려요. 반대로 다른 컴퓨터에서 올린 「문구 수정」 같은 새 커밋은 git pull로 받아서 내 폴더에 합칩니다. 왼쪽 세 칸이 내 컴퓨터, 오른쪽 한 칸이 인터넷입니다.

> 곁들일 이야기 — 온라인 쇼핑으로 치면 이렇습니다. 작업 폴더는 매장 구경, git add는 장바구니 담기, git commit은 결제, git push는 택배 발송. 장바구니가 있으니까 고친 파일 중에 일부만 골라서 한 번에 저장할 수 있어요. 보기만 하고 안 사는 것도 자유고요.

## 144 · 코드 변경과 diff
Git은 이 네 구역의 내용을 계속 비교합니다. 버튼 색을 navy에서 orange로 바꾸면, 작업 폴더와 스테이징 사이에 빼기 한 줄, 더하기 한 줄이 diff로 나타나요. 한 줄 더 넣으면 더하기가 하나 늘고요. git add로 담으면 이번엔 스테이징과 로컬 저장소 사이에 차이가 보이고, commit하고 push까지 하면 모든 구역이 같아져서 「차이 없음」이 됩니다. 빨간 빼기는 지운 줄, 초록 더하기는 새로 생긴 줄입니다.

> 곁들일 이야기 — 워드 「변경 내용 추적」 써 보셨죠. 지운 글자엔 취소선, 새로 쓴 글자엔 밑줄. 같은 생각입니다. 1-6에서 Claude Code가 코드를 고칠 때도 이런 빼기 · 더하기 화면을 보여 줘요. 이 표시만 읽을 줄 알면 뭐가 바뀌는지 바로 확인할 수 있습니다.

## 145 · 커밋 시점
그럼 언제 커밋하느냐. 기준은 세 가지입니다. 「로그인 버튼 동작」처럼 기능 하나가 됐을 때. 디자인을 갈아엎는 것처럼 크게 바꾸기 전. 그리고 브라우저로 보고 이상 없다는 확인이 끝났을 때. 흐름으로 보면 요청하고, 확인하고, 커밋하고, 다음 요청. 이 고리를 1-6에서 태스크마다 반복합니다.

> 곁들일 이야기 — 예를 들어 AI한테 「전체 색상 바꿔 줘」 했는데 결과가 영 이상하게 나왔다고 해 보죠. 바로 앞에 커밋해 뒀다면 「방금 고친 거 취소해 줘」 한마디로 돌아갑니다. 안 해 뒀다면? 원래 모습이 뭐였는지부터 기억을 더듬어야 합니다. 보통 기억 안 납니다.

## 146 · 실습 1-5 · 첫 커밋
자, 직접 해 봅시다. 목표는 기획서.md와 개발계획.md가 든 내 폴더를 Git으로 기록하기 시작하는 겁니다. VS Code로 1-3, 1-4에서 쓰던 프로젝트 폴더를 열고, 두 파일이 있는지 먼저 확인하세요. 그다음 Claude Code에 Git을 시작하고 첫 커밋을 남겨 달라고 요청하고, 커밋 기록을 보여 달라고 합니다. 마지막으로 개발 계획 한 줄을 일부러 고친 다음 되돌려 달라고 해 보세요. 일부러 망가뜨려 보는 게 이번 실습의 하이라이트입니다. 기록에 첫 커밋이 하나 있고, 되돌린 뒤 개발계획.md가 커밋 상태와 같으면 완료입니다.

## 147 · 실습 1-5 순서
순서를 다시 짚어 볼게요. 폴더 열고 Claude Code를 실행합니다. Git 시작과 첫 커밋을 요청하고, 기록을 보여 달라고 합니다. 그다음 개발계획.md에서 아무 줄이나 직접 고치고 저장한 뒤, 「방금 고친 거 취소해 줘」라고 요청합니다. 기록에 내 메시지가 보이고, 고친 줄이 원래대로 돌아오면 성공이에요. 막히기 쉬운 곳이 두 군데 있습니다. 컴퓨터에 Git이 없다고 나오면, Claude Code한테 「Git 설치 방법 알려 줘」라고 물어보세요. 처음 커밋할 때 이름이랑 이메일을 물어보면, GitHub 가입할 때 쓴 정보를 넣으시면 됩니다.

> 곁들일 이야기 — 이름이랑 이메일을 왜 묻냐면, 아까 본 커밋 구성의 「누가」 칸을 채우려는 겁니다. 한 번 넣어 두면 그다음 커밋부터는 알아서 들어가요.

## 148 · 실습 1-5 요청 항목
요청할 때는 세 가지만 담으면 됩니다. 목표는 이 폴더를 Git으로 관리하고 첫 커밋 남기기. 대상은 기획서.md와 개발계획.md. 메시지는 뭘 담았는지 한 줄. 문장을 토씨 하나까지 맞출 필요는 없어요. 이 세 가지만 들어가 있으면 됩니다.
