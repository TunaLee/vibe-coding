## 93 · Git · GitHub 기초

## 94 · 1부 커리큘럼
전체 흐름으로 보면 다섯 번째 칸입니다. 1-1부터 1-4까지는 뭘 만들지 정했고, 1-6부터는 실제로 만들고 배포합니다. 1-5는 그 사이에서 작업 기록을 남기는 습관을 붙이는 단계예요. 공통 예제 미니 노션도 똑같이 첫 커밋부터 시작합니다.

> 곁들일 이야기 — 바이브코딩에서는 AI가 한 번에 파일 여러 개를 고칩니다. 내가 손으로 고칠 때는 어디 고쳤는지 대충 기억이라도 나는데, AI가 고치면 그것도 없죠. 그래서 「어디가 바뀌었나, 원래대로 돌릴 수 있나」가 훨씬 중요해집니다. 이 단원을 코드 작성보다 먼저 두는 이유예요.

## 95 · 파일 이름 버전 관리
먼저 다들 겪어 본 장면부터요. 발표자료 하나 고치다 보면 _v2, _최종, _최종_수정, _진짜최종, _진짜진짜마지막까지 사본이 늘어납니다. 보면서 웃으시는 분들, 다 압니다. 그 폴더 있으시죠. 이렇게 관리하면 세 가지가 어렵습니다. 어느 게 최신인지 날짜나 내용을 열어 봐야 알고, 뭐가 바뀌었는지는 두 파일을 나란히 놓고 눈으로 비교해야 하고, 중간 사본을 지웠으면 그 상태로는 다시 못 돌아갑니다. Git이 바로 이 문제를 푸는 도구입니다.

> 곁들일 이야기 — 팀장님이 「사흘 전 버전에 있던 표 다시 살려 주세요」 하시면, 사본 여섯 개를 하나씩 열어서 표 있는 파일을 찾아야 합니다. 구글 문서나 워드의 「버전 기록」 기능이 이 수고를 줄이려고 나온 거고, Git은 같은 일을 폴더 전체 단위로 해 줍니다.

## 96 · 세이브 포인트
Git을 이해하는 제일 쉬운 방법은 게임의 세이브 포인트입니다. 보스 방 앞에서 저장해 두면, 져도 그 지점부터 다시 시작하죠. 처음부터 다시 하라고 하면 게임기 던지고 싶어집니다. Git에서 저장하는 일을 커밋, 저장 슬롯에 붙이는 이름을 커밋 메시지라고 합니다. 저장 목록은 기록, log고요, 저장 시점을 불러오는 게 되돌리기입니다. 그리고 게임 클라우드 저장처럼 기록을 인터넷에 올려 두는 곳이 GitHub입니다.

> 곁들일 이야기 — 게임기를 바꿔도 클라우드 저장 덕분에 이어서 할 수 있잖아요. GitHub에 올려 둔 기록도 마찬가지로, 노트북이 고장 나도 다른 컴퓨터에서 그대로 받아서 이어 작업할 수 있습니다.

## 97 · 커밋 구성
커밋 하나를 뜯어 보겠습니다. 왼쪽은 이 커밋을 남긴 순간의 화면이에요. 로그인 버튼이 막 생겼죠. 오른쪽이 그 순간을 저장한 커밋 한 개입니다. 위에서부터 고유 번호 8fcbe80, 커밋마다 다르게 붙는 번호라 해시라고 부릅니다. 메시지 「버튼 추가」, 나중에 돌아갈 시점을 찾는 이름표예요. 시각과 작성자, 언제 누가 했는지. 작성자는 조금 뒤 실습에서 등록할 내 이름이 들어갑니다. 마지막이 바뀐 내용, index.html에 버튼 한 줄이 더해졌다는 기록이에요. 이 중에서 사람이 신경 쓸 건 메시지 하나입니다. 나머지는 Git이 알아서 채웁니다.

> 곁들일 이야기 — 메시지를 전부 「수정」이라고만 남기면 어떻게 될까요. 기록이 스무 개 쌓였을 때 「수정, 수정, 수정…」 중에 어디로 돌아갈지 알 수가 없습니다. 파일 이름 「진짜최종」이랑 다를 게 없죠. 「로그인 버튼 추가」처럼 뭘 바꿨는지 한 줄이면 충분합니다.

## 98 · 커밋 기록 쌓기
커밋은 이렇게 아래에서 위로 쌓입니다. 첫 화면 완성, 버튼 추가, 색상 수정, 이 순서로 세 번 저장했어요. 오른쪽은 같은 기록을 터미널에서 git log --oneline으로 본 모습인데, 최신 커밋이 맨 위에 나옵니다. 앞에 붙은 문자 일곱 개가 방금 말씀드린 고유 번호예요.

> 곁들일 이야기 — 카톡 대화방을 위로 쭉 올려 보면 언제 무슨 말이 오갔는지 다 남아 있죠. 비슷합니다. 다만 Git 기록은 「뭘 바꿨는지」만 모아 둔 대화방이에요. 잡담은 없습니다.

## 99 · 커밋으로 되돌리기
커밋이 왜 좋은지 화면으로 보겠습니다. v1 첫 화면 완성, v2 버튼 추가, v3 색상 수정. 커밋마다 그 순간의 화면이 통째로 저장돼 있어요. 그다음에 뭔가를 고쳤는데 화면이 깨졌습니다. 아직 커밋은 안 했고요. 이럴 때 「마지막 커밋으로 되돌려 줘」 한마디면, 화면이 v3 색상 수정 상태로 돌아옵니다. 사라지는 건 커밋 전에 한 실수뿐이에요. 게임에서 보스한테 지면 마지막 세이브 포인트에서 다시 시작하는 것과 똑같습니다. 그래서 잘 될 때마다 커밋, 이게 1-6에서 계속 반복할 습관입니다.

## 100 · Git과 GitHub
이제 GitHub입니다. 왼쪽 점선이 내 컴퓨터예요. Git은 여기서 기록을 만드는 프로그램입니다. 방금 v3 커밋을 새로 남겼죠. 그런데 이 기록은 아직 내 컴퓨터에만 있습니다. 노트북에 커피 쏟으면 같이 날아가요. 그래서 git push, 올리기를 합니다. 그러면 v3이 가운데 GitHub로 복사돼요. GitHub는 인터넷에서 이 기록을 보관해 주는 서비스입니다. 일단 GitHub에 올라가면 다른 컴퓨터에서 같은 기록을 받아 이어서 작업할 수 있고, 이걸 git pull, 받아 오기라고 합니다. 그리고 1-7에서 배울 Vercel도 GitHub에 있는 기록을 가져가서 배포해요. 아래 비유처럼 생각하시면 쉽습니다. Git은 휴대폰 사진첩, GitHub는 클라우드 백업, push는 백업 올리기, pull은 다른 기기에서 받기. Free 요금제로도 비공개 저장소를 개수 제한 없이 만들 수 있습니다.

> 곁들일 이야기 — Git이랑 GitHub, 이름이 비슷해서 같은 걸로 많이들 헷갈립니다. Git은 프로그램 이름이고, GitHub는 그 기록을 맡아 주는 서비스 이름이에요. 참고로 GitHub는 2018년에 마이크로소프트가 인수했습니다.

## 101 · Git 작업 흐름
실제로 기록이 어떻게 움직이는지 애니메이션으로 보겠습니다. 작업 폴더에서 파일을 고치면, git add로 커밋할 파일을 스테이징 영역에 담습니다. 그다음 git commit으로 로컬 저장소에 기록을 남기고, git push로 그 기록을 GitHub에 올려요. 반대로 다른 컴퓨터에서 올린 「문구 수정」 같은 새 커밋은 git pull로 받아서 내 폴더에 합칩니다. 왼쪽 세 칸이 내 컴퓨터, 오른쪽 한 칸이 인터넷입니다.

> 곁들일 이야기 — 온라인 쇼핑으로 치면 이렇습니다. 작업 폴더는 매장 구경, git add는 장바구니 담기, git commit은 결제, git push는 택배 발송. 장바구니가 있으니까 고친 파일 중에 일부만 골라서 한 번에 저장할 수 있어요. 보기만 하고 안 사는 것도 자유고요.

## 102 · Git 작업 요청
add, commit, push, 명령어 이름이 꽤 나왔는데 외우실 필요 없습니다. 시험 안 봐요. 바이브코딩에서는 Claude Code한테 말로 시킵니다. 「지금 상태 커밋해 줘」 하면 git add랑 git commit이 실행되고 메시지도 Claude가 씁니다. 「커밋 기록 보여 줘」는 git log, 되돌리기는 두 가지예요. 아직 커밋 전이면 「방금 고친 거 취소해 줘」, git restore. 이미 커밋했으면 「마지막 커밋 되돌려 줘」, git revert인데, 이건 기록을 지우지 않고 「되돌림」이라는 새 커밋을 하나 더 남깁니다. 명령 실행은 Claude Code가 하고, 사람은 결과가 맞는지만 확인합니다.

> 곁들일 이야기 — 엑셀 함수 이름을 몰라도 「합계 내 줘」 하면 되는 것과 비슷합니다. 다만 이름을 한 번 들어 둔 덕분에, Claude가 「git revert를 실행했습니다」라고 답할 때 무슨 일이 일어났는지 알아들을 수 있죠. 그 정도면 충분합니다.

## 103 · 커밋 시점
그럼 언제 커밋하느냐. 기준은 세 가지입니다. 「로그인 버튼 동작」처럼 기능 하나가 됐을 때. 디자인을 갈아엎는 것처럼 크게 바꾸기 전. 그리고 브라우저로 보고 이상 없다는 확인이 끝났을 때. 흐름으로 보면 요청하고, 확인하고, 커밋하고, 다음 요청. 이 고리를 1-6에서 태스크마다 반복합니다.

> 곁들일 이야기 — 예를 들어 AI한테 「전체 색상 바꿔 줘」 했는데 결과가 영 이상하게 나왔다고 해 보죠. 바로 앞에 커밋해 뒀다면 「방금 고친 거 취소해 줘」 한마디로 돌아갑니다. 안 해 뒀다면? 원래 모습이 뭐였는지부터 기억을 더듬어야 합니다. 보통 기억 안 납니다.

## 104 · Git 준비
실습 전에 준비할 게 있습니다. Git으로 기록하고 GitHub에 올리려면 네 가지가 필요해요. Git 설치, GitHub 계정, 작성자 등록, GitHub 로그인. GitHub 계정은 1-2에서 만들었죠. Git은 없으면 Claude Code에 「Git 설치해 줘」라고 하면 됩니다. 나머지 둘이 이번에 새로 하는 겁니다. 작성자는 커밋에 남는 「누가」이고, 로그인은 GitHub에 올릴 때 필요해요. 둘 다 처음 한 번만 하면 다음부터는 알아서 됩니다.

## 105 · Git 작성자 등록
아까 커밋 구성에 「누가」 칸이 있었죠. 그 칸을 채우는 게 작성자 등록입니다. 이름과 이메일을 이 컴퓨터에 한 번 적어 두면, 그다음 커밋부터 자동으로 들어가요. 값은 GitHub 가입할 때 쓴 이름과 이메일로 하세요. 그래야 GitHub에서 커밋이 내 계정과 연결돼 보입니다. 명령은 화면 같은 git config인데, 직접 칠 필요 없이 「Git 작성자를 내 GitHub 이름 · 이메일로 등록해 줘」라고 하면 Claude Code가 이름과 이메일을 묻고 실행합니다.

## 106 · GitHub CLI (gh)
GitHub 로그인에 쓰는 도구가 GitHub CLI, 줄여서 gh입니다. GitHub가 공식으로 만든 명령 도구예요. 웹사이트에서 버튼 눌러 하던 저장소 만들기, 올리기를 명령으로 할 수 있게 해 줍니다. 명령은 Claude Code가 실행하니까 외울 필요 없습니다. 우리가 할 일은 처음 한 번 설치하고 로그인해 두는 것뿐이에요. 설치도 Claude Code에 「GitHub CLI 설치해 줘」라고 하면 됩니다. 맥이면 brew, 윈도우면 winget 명령을 보여 주면서 허용할지 물어볼 거예요. 윈도우는 설치 뒤에 VS Code를 한 번 껐다 켜야 gh를 알아봅니다.

> 곁들일 이야기 — 새 프로그램을 깔았는데 아이콘이 안 보여서 재부팅하니까 보였던 경험, 한 번쯤 있으시죠. VS Code도 비슷합니다. 이미 열려 있던 창은 설치 전 상태를 기억하고 있어요. 다시 열어야 새로 깐 도구를 알아봅니다.

## 107 · gh 로그인
설치했으면 gh를 내 GitHub 계정이랑 연결합니다. 이게 「브라우저 로그인 연동」이에요. 1-7에서 GitHub에 올릴 때 이 연결을 씁니다. Claude Code에 「GitHub 로그인 도와줘」라고 하면 로그인 명령을 실행하고, 화면에 짧은 코드를 보여 주면서 브라우저를 열어 줍니다. 브라우저에 그 코드를 넣고 승인하면 연결 끝이에요. 「로그인됐는지 확인해 줘」라고 하면 확인까지 해 줍니다. 혹시 여기서 멈춰 있으면 손 들어 주세요. 같이 하겠습니다. 여기서 중요한 게 하나 있습니다. 브라우저 승인은 반드시 사람이 직접 합니다. 비밀번호를 Claude한테 알려 주지 않아요. Claude는 연결된 권한으로 명령만 실행합니다.

> 곁들일 이야기 — 거실 TV에서 넷플릭스나 유튜브 로그인할 때, TV에 뜬 코드를 휴대폰에 입력해 보셨죠? gh auth login도 같은 방식입니다. 리모컨으로 비밀번호 한 글자씩 치는 고행 대신, 이미 로그인된 휴대폰이나 브라우저에서 「이 기기 허락」만 누르는 겁니다.

## 108 · 실습 1-5 · 첫 커밋
자, 직접 해 봅시다. 목표는 기획서.md와 개발계획.md가 든 내 폴더를 Git으로 기록하기 시작하는 겁니다. 폴더는 1-3부터 쓰는 mini_notion_v2 그대로예요. 먼저 작성자를 등록하고 GitHub에 로그인해 둡니다. 그다음 Claude Code에 Git을 시작하고 첫 커밋을 남겨 달라고 요청하고, 커밋 기록을 보여 달라고 합니다. 기록에 첫 커밋이 하나 있고 작성자가 내 이름이면 완료입니다.

## 109 · 실습 1-5 순서
세 단계입니다. 먼저 모드를 Plan에서 「수정마다 승인」으로 되돌리세요. Plan이면 명령을 실행하지 않습니다. 1번, 「Git 작성자를 내 GitHub 이름 · 이메일로 등록해 줘」. 2번, 「GitHub 로그인 도와줘」 하고 브라우저에서 승인. 3번, 「Git으로 관리하고 첫 커밋 남겨 줘」, 이어서 기록 보기. 컴퓨터에 Git이 없다고 나오면 「Git 설치해 줘」라고 하세요. 로그인에서 멈추면 손 들어 주세요. 메시지는 「기획서 · 개발 계획 첫 버전으로 해 줘」처럼 직접 정해 주면 나중에 찾기 쉽습니다.

## 110 · 실습 1-5 · 1단계 작성자 등록
먼저 작성자 등록입니다. 「Git 작성자를 내 GitHub 이름 · 이메일로 등록해 줘」. 이름과 이메일을 물어보면 GitHub 가입 정보를 넣으세요. 그러면 git config 명령을 보여 주면서 허락을 구합니다. 이번만 허용할 수도 있고, 같은 종류 명령은 다음부터 묻지 않게 할 수도 있어요. 처음엔 뭘 하는지 눈에 익을 때까지 하나씩 허용하면서 보세요. 아, 1-3 · 1-4에서 Plan으로 바꿔 둔 모드는 「수정마다 승인」으로 되돌리고 보내세요.

## 111 · 실습 1-5 · 2단계 GitHub 로그인
다음은 GitHub 로그인. 「GitHub 로그인 도와줘」. gh가 없으면 설치부터 하자고 할 거예요. 허용하세요. 그다음 화면에 코드가 나오고 브라우저가 열립니다. 코드를 넣고 승인. 끝나면 「로그인됐는지 확인해 줘」로 내 계정 이름이 보이는지 봅니다. 여기서 멈춰 있으면 손 들어 주세요.

## 112 · 실습 1-5 · 3단계 Git 시작 · 첫 커밋
이제 「Git으로 관리하고 첫 커밋 남겨 줘」. 명령을 보여 주면서 허락을 구하면 허용하세요. 첫 커밋이 만들어지면 커밋 번호와 메시지, 어떤 파일이 담겼는지 알려 줍니다. 이어서 「커밋 기록 보여 줘」. 번호, 누가, 언제, 무슨 메시지로. 작성자 칸에 방금 등록한 내 이름이 보이면 됩니다. 지금은 하나지만 1-6에서 기능 하나 만들 때마다 한 줄씩 늘어날 거예요. 화면으로 같이 보겠습니다.

## 113 · 실습 1-5 확인
두 가지만 확인합니다. 커밋 기록에 커밋이 하나 있고 작성자가 내 이름인가. GitHub 로그인이 됐나, 「로그인됐는지 확인해 줘」로 내 계정이 보이면 됩니다. 커밋 번호는 사람마다 다르게 나오니까 옆자리랑 달라도 괜찮아요. 둘 다 「예」면 끝입니다. 되돌리기는 1-6에서 앱을 만들다 망가졌을 때 직접 써 봅니다. 다음 단원에서는 드디어 이 폴더에 앱을 만들고, 기능 하나가 될 때마다 커밋을 쌓아 갑니다.

> 곁들일 이야기 — 이 첫 커밋이 게임으로 치면 첫 번째 세이브 포인트입니다. 1-6에서 뭘 망가뜨리든, 최소한 기획서랑 개발 계획만 있던 이 상태로는 언제든 돌아올 수 있어요. 마음 놓고 망가뜨리셔도 됩니다.
